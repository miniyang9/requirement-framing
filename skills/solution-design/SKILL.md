# Solution Design（L2–L5）

上游是 `requirement-framing`，输入是一份**已签的 frame**。
下游是 `incremental-delivery`，交给它的是架构、契约、决策记录。
**本 skill 不写功能代码，不切任务卡。**

## 门禁：先找已签的 frame，再做体检

1. 找 `docs/frame/*.md`，读顶部 `状态：`
2. 有多份已签 → **问用户指认**，不要按修改时间猜
3. 先读 `## 0. 承重事实`，再读全文

**只有"已签"能进。** 待答 / 待签 → 退回 `requirement-framing`，一句话说明，不要就地脑补需求。

### frame 体检（八条，缺一退回）

| # | 检查 | 不过怎么办 |
|---|---|---|
| 1 | `状态：已签` | 退回 `requirement-framing` 签字 |
| 2 | `## 0. 承重事实` 至少一条，且每条带锚点。**体量档是 T1 时可接受等效物**：五问里的「最大歧义」与「不做」两节齐备（T1 按 `requirement-framing` 的减配条款不写 §0） | 退回 `requirement-framing` 补 §0；或把 T1 改成 T2 |
| 3 | 头部三行齐，且 `范围方案` ∈ {最小, 正规, 平台化}（不含「待选」、不是三项全列） | 退回 `requirement-framing` 补 |
| 4 | "不做"的条目带了理由 | 退回 `requirement-framing` 补理由 |
| 5 | **没有未关闭的 `UPSTREAM-xx`**（关闭办法见「上游异议」） | 先关闭，不许带病设计 |
| 6 | 签字块三字段齐：`签字人` / `签字日期`（可解析）/ `版本` | 退回 `requirement-framing` 补签字块 |
| 7 | 每条承重事实带四类来源之一（`[你说过]`/`[推断]`/`[代码]`/`[外部]`）；T1 走等效物时不强求 | 退回补来源 |
| 8 | **复审已关闭**：`docs/frame/<slug>.review.md` 存在，且没有未闭环的阻断项（未闭环必须有人类裁决记录） | 退回 `requirement-framing` 走复审 |

**有一条额外的验：会改变 01 结构的外部依赖，必须在 B 验掉。** 判据——"如果这条依赖不成立，01 的分层/契约数量/顺序会变吗？"会变（比如没有 SMTP 中继，notify 就不是"发提醒"而是"生成清单"），就先去探一次；探不了就记一条 `UPSTREAM`，不许按猜的往下设计。

**手写的 frame 也要过这八条。** "看起来完整"不是通过条件——`requirement-framing` 的第 4 步自检是它的承诺，不是你的验收；两边各做一次。

### 上游异议：发现 `requirement-framing` 判错了怎么办

在 L2 你可能会发现上游判定有误。最常见的两种：

- **体量档判小了**：frame 判 T1，但它实际跨三个可独立验收的单元——五问压不住，§0 也没写。
- **范围方案和验收打架**：frame 选了「最小」，但验收里要的东西只有「正规」才有。

处理方式：

- **不许改 frame**（那是 `requirement-framing` 的产物，签字主体不同）
- 在 `03-decisions.md` 记一条 `UPSTREAM-01`：哪条判错、依据、建议改成什么
- **交付时明确告知用户**："这条需要回 `requirement-framing` 重签"
- 若这条异议会改变 01 的结构（边界、契约数量、顺序）→ **先解决再继续**，不许带病设计

**异议有 open / closed 两个状态，关闭只有两条路：**

| 关闭方式 | 怎么写 |
|---|---|
| 用户回 `requirement-framing` 重签了 frame，你复核通过 | 在该条后追加 `closed: <日期> 已重签，复核通过` |
| 用户明确说不改、接受现状 | 在该条后追加 `closed: <日期> 用户接受现状` |

**你不能自己关。** 没人处理就一直挂着——体检第 5 条会一直拦你，这是设计如此：**带着未决异议往下设计，等于把风险焊进架构。**

**没有 frame 时**：不许"先讨论一下架构再说"。哪怕用户直接问"该怎么分层"，也先退回 L1——否则你设计的是一份口头需求的架构。

**例外**：用户明说只是"概念咨询、不入库"，那就当咨询答，不进流程，也不产出 `docs/arch/`。

## 两个轴沿用，不重定

体量档、范围方案在 L1 已经定了。这里只**消费**：

- **体量档**决定要不要全走（T1 通常只走一部分）
- 想改任何一个轴 → 回 `requirement-framing` 改 frame，不要在这里偷偷调整

> **设计做多深，是这里自己判断的，不是从上游读来的。** 四个判断各有触发点，长在对应步骤旁边：
> 图怎么分（第 1 步）、契约怎么写（第 2 步）、决策记多细（第 4 步）、骨架放哪（第 4 步，那张后果成本表）。

## 第 1 步：L2 架构 —— 五个问题

每个都要给"你选了哪个、为什么"，不写教程。

| # | 问题 | 定不了会怎样 |
|---|---|---|
| 1 | **边界按什么切？** 变更频率 / 数据所有权 / 团队，选一个主判据 | 会按"文件类型"切，然后每个需求都横跨所有模块 |
| 2 | **跨层数据只有一种形状吗？**（世界快照 / 事件 / 模型） | 每层各造一套，接起来时才发现一直在翻译 |
| 3 | **失败在哪一层被隔离？** 一个外部超时能打穿到哪 | 一个第三方抖动，整条链路停摆 |
| 4 | **哪些是契约？** 会被两个以上单元同时读写的 | 没有唯一写者，谁都能改，改完没人知道 |
| 5 | **骨架最薄能薄到什么程度？** 薄到只够证伪约定 | 骨架膨胀成半个产品，改不动 |

产出：**1–3 张图** + 每问的一句话答案。

> **画哪些视图、怎么保证可重建** → 读 `references/diagrams.md`。动手画图之前必读。

## 第 2 步：L3 契约

判据只有一条：

> **会被两个以上单元同时读写的东西，必须是契约；其余不该是。**

**先把两个词分开**：*契约*是那份约定，*契约文档*是记录它的文件。**契约一定有，02 一定存在**——只是形状长在代码里，02 记指针和约定。

三条硬规矩：

- **每个契约一个唯一写者**，其余只读——这是唯一能防"热心地各自改接口"的结构性手段
- **形状写成代码里的类型**（编译器替你守）；**约定写成 02 的条目**（代码守不住的那些）
- **冻结时机**：第一个消费者要开工之前，不是"设计全部完成之后"

**02 从第一天就写成索引，不写字段。** 文件开头必须先有冻结行：

```
冻结：<YYYY-MM-DD>    冻结人：<角色>
```

没有这一行，执行阶段无法判断"能不能开工"。然后每个契约一行，形状那一栏本来就是一个指针：

| 契约 | 形状 | 唯一写者 | 约定（不变量 · 封闭集合 · 错误码） | 版本 | 冻结理由 |
|---|---|---|---|---|---|
| `Repo` | 待落地 → `core/models.py` | Fetcher（两实现互斥） | views 非空；url 规范化 | v1 | 流水线入口形状 |

落地时只改一格：`待落地` → `已落地 → core/models.py:31`。

**谁写形状**：实现者在第一次落地时把类型写进代码——不是 `solution-design`，也不是契约的写者。但它必须满足这一行的约束（唯一写者、封闭集合、不变量）；**新增实现内部字段不算改契约**。

**没有"某天把 02 改写成指针"这个动作**——那种任务一定会忘，而且没人负责检测"落地"这个时刻。谁改：执行阶段每片收尾时（`incremental-delivery` 的职责，它才知道代码落在哪）。

代码表达不了的——**唯一写者、不变量、冻结理由、错误码映射**——永久留在 02。

六个常见契约、桩的要求、单人档等价物：读 `references/contracts.md`。

## 第 3 步：L4 决策记录

一行一条，**五列**：`编号 / 日期 / 决定 / 理由 / 否决了什么`。

**编号是硬要求**：没有编号，"只增不删"就落不了地——被推翻时你没法写"推翻 ADR-07"。

**"否决了什么"不能省**——它挡住的是六周后你自己把已否掉的方案重新提出来。

不写故事，不写背景铺垫。

**ADR 的边界：先分清改的是基线还是验证状态。**

| 改的是 | 例子 | 处置 | 重签 |
|---|---|---|---|
| **基线** | 部署口径、范围、架构、契约、加 / 减功能 | 回对应层改，重签 | **要** |
| **验证状态** | 没测、没条件测、测了不达标但人类接受 | 记偏离 + ADR + frame 的 `## 偏离` 节 | 不用 |

**判据一句话：方案的结论会不会变？**

- 不会变，只是「还没证据」或「证据不达标」→ **验证状态** → 记偏离，不动基线
- 会变 → **基线** → 重签

**不许用 ADR 悄悄改基线。** ADR 里出现「覆盖 frame X」这种字样就是越线信号——那是变更，要有人重新签字。

**但「记」这一步不许省。** 偏离必须三件齐：① 写进 frame 的 `## 偏离` 节（只增不改）② 一条 ADR 含**人类原话** ③ 交付节逐项列为已知风险。

（行业依据：配置管理标准 EIA-649 把 Deviation / Waiver / Change Request 分作三件事——前两个不动基线，只有变更要重走审批。测试侧对应 ISTQB 的「残余风险」，由利益相关者接受并登记。）

## 第 4 步：L5 骨架判据

> **骨架是 L2/L3 的验收测试，不是实现的开始。** 产出是"架构是否成立"这个判断，不是功能。

要不要单独成一级，看**第一个端到端验证点是否昂贵或不可逆**：

| 后果成本 | L5 形态 |
|---|---|
| 便宜（可重跑、可回滚） | **合并**：L5 与第一片重合，不单独成级 |
| 中等（有真实副作用但可承受） | **正常**：在真实环境跑一条最薄路径 |
| 昂贵或不可逆（钱、生产数据、对外承诺） | **前移并换环境**：先在模拟/沙箱里跑，且成为接真实环境的硬性前置条件 |

推论：**L5 的位置不固定。** 后果越不可逆，它越靠前——对交易系统，回测骨架几乎排在建契约之前。

**01 必须给 L5、验收、落盘形状各留一节**，否则执行侧无处可读，"验"必然退化成自证：

```
## 骨架（L5）
S1 … S4：每条一句"验什么" + 一个通过阈值（数字或布尔）

## 验收
两段都要写：
- **frame 的验收标准 → 证据**（需求级：每条判据对应什么命令 / fixture / 日志字段）
- **L2 五问 → 证据**（架构级：每问对应什么）

## 落盘形状
目录树 + 每个产物落在哪（执行侧不另定目录结构）
```

**没有这三节，01 不算完成。**

## 造还是用（技术选型）

**LLM 写代码太容易，所以默认偏向必然是「我自己写」——它没有动机去找包。** 这一节是用来平衡那个偏向的。

### 造之前先问

自造一个非平凡部件之前，答三句，写进 03 的一条 ADR：

1. **它是商品能力还是差异点？**
   - 商品（WebSocket / 认证 / 日期 / HTTP / 序列化 / 日志 / 调度）→ **默认用现成的**
   - 差异点（业务规则、核心算法）→ 默认自造
2. **现成的代价**：维护状态、license、供应链、体积
3. **自造的代价**：不只是写，还有边界情况（协议分片 / 时区 / 编码 / 并发）和长期维护

**判据：这一块出问题时，责任落在谁身上？** 用现成的，坑在上游；自造，坑在自己。

**不许拿「我写得出来」当理由。**

**触发条件**（达到就必须先查一眼，不用每件小事都论证）：

- 预计超过 ~200 行，或
- 涉及协议 / 加密 / 时间与时区 / 字符编码 / 并发这五类「细节决定成败」的领域

查的方式：`web_search` + 看包的主流程和最近提交。

### 引入依赖：先分两类

**先分清是「不可用」还是「有风险」**——两者处理完全不同。

#### A. 不可用（法律或供应链上的硬伤）

| 查什么 | 什么算不可用 | 怎么办 |
|---|---|---|
| **License** | 没有 LICENSE 文件（保留所有权利，**无声明 ≠ 免费**）；GPL / AGPL 且项目闭源 | **换一个** |
| **供应链** | 包名近似热门包（typosquat）；repository 链接和官方对不上；postinstall 有网络动作或原生编译 | **换一个** |

**默认按闭源处理**——不需要为了判断它去问人。用户说过这个项目是开源的，GPL / AGPL 才可用。

**这一类先换，不要停下来问。** 只有「找不到任何替代」时才停——那时选择真的只有人类能做。

#### B. 有风险但可用

| 查什么 | 信号 | 处理 |
|---|---|---|
| **已知漏洞** | `npm audit` / `pip-audit` / GitHub Advisory 报 high 或 critical | ① 有修复版本 → 升上去 ② 有等价替代 → 换掉 ③ 都没有 → **记账继续** |
| **还活着吗** | 12 个月无提交 / 最近 release 超 2 年且主版本没动 / 有 abandoned 声明 | 同上三步 |

**这一类不停。** AI 找漏洞让「有 high」变成高频事件，硬拒会把大部分包卡死。**记账，在发布时一起还。**

#### C. 两项必做（两类都要）

| # | 做什么 | 判据 |
|---|---|---|
| 1 | **隔离** | 只被 **1 个文件** import → 可以不包；被 **2 个及以上** import → **必须包一层 adapter**，之后只许 adapter 里出现这个包名 |
| 2 | **记账** | 03 一条 ADR：为什么用、替我省了什么（多少行 / 多少天）、传递依赖数、换掉它要改几个文件；属于 B 类的，标 `已知风险：…` |

**隔离是这一节里最重要的一条。** 一个包再流行，一旦渗进 20 个文件，它就成了你的架构——**替换成本才是真正的成本**。

**人类判断不在这里发生。** 这里的判断全部推迟到交付前的发布确认——那时本来就要人拍板，不新增关卡。

## 四条硬约束

- **唯一写者**：每个契约只有一个写者，其余只读
- **骨架是验收测试**：跑不通就回 L2/L3，不往下走
- **图必有重建路径**：源 + 渲染器 + 命令，缺一样都不算产出
- **看到依赖链 = 缺契约**：如果后一步必须等前一步的真实产出，那前一步的产出本应是冻结物，不是运行时依赖

## 交棒

| 级 | 谁做 | 交付物 |
|---|---|---|
| L2–L5 | **本 skill** | 架构一页 + 契约 + 决策记录 |
| 执行（选片 / 写 / 验 / 收尾） | `incremental-delivery` | 每片五行台账（做了 / 没做 / 下次 / 证据 / 返工） |
| 并行片（判得出 ≥2 条不相交的线） | `incremental-delivery` | 任务卡 |

**本 skill 不产出任务卡。** 用户要"把它拆成任务"时，说明该进 `incremental-delivery` 了。

## 设计侧红旗

| 你正在想的 | 现实 |
|---|---|
| "架构等写完再补" | 架构不是细化，它是并行的前提 |
| "这就是几个独立任务" | 那你应该能画出星形 DAG；画不出来就是缺契约 |
| "先把代码骨架搭起来" | 骨架的产出是判断，不是功能 |

> **改了设计要连带改哪里、怎么解冻、交付前查什么** → 读 `references/change-propagation.md`。改设计或交付之前必读。
