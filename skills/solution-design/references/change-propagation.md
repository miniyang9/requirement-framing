# 变更传播 / 解冻 / 交付前三查（从 SKILL.md 拆出）

> **什么时候读**：改已产出的设计之前，或交付之前。

---

## 变更传播

改一处必须连带改另一处，否则三份文档会互相矛盾。

| 变了什么 | 必须连带 | 谁记 |
|---|---|---|
| frame 的 §0 承重事实 | 01 的五问可能整段作废 | **回 `requirement-framing` 重签**，不在 `solution-design` 就地改 |
| 01 的边界 / 数据形状 | 02 的契约增删；01 的图重出（改 JSON 再渲染） | `solution-design` |
| 02 的契约字段 | 03 记一条；下游的验收夹具 | `solution-design` |
| 03 的某条决策被推翻 | **不删旧条**，新增一条写明为何推翻 | `solution-design` |
| 执行中发现设计缺口 | 回 `solution-design` 补 01/02，**不回 `requirement-framing`、也不就地改** | `incremental-delivery` → `solution-design` |
| **用户在 L2/L3 期间加需求** | 回 `requirement-framing` 改 frame **并重签**；不许在 `solution-design` 就地扩范围 | `requirement-framing` |

两条铁律：

- **决策只增不删。** 删了就没人知道曾经否决过什么，六周后会重开。
- **图的改动只走 JSON。** PNG / HTML 是产物，手改等于制造第二份真相。

### 解冻程序

冻结不是单向门，但解冻要付账：

1. `03` 记一条：谁要求解冻、哪条契约、为什么
2. 改 `02` 的那一行（保留旧值，加"解冻于 X"）
3. 通知执行侧：**已经过验收的片，依赖这条契约的必须重验**

没有第 3 步的解冻，等于让已验收的代码和契约悄悄脱钩。

## 交付前三查

三份文档之间最容易互相打脸，交之前对一遍：

| 查什么 | 对不上意味着 |
|---|---|
| 01 的契约清单 vs 02 的唯一写者表 | 有一个契约没人写，或有两个写者 |
| 02 的字段 / 封闭集合 vs 03 的相关决策 | 决策说改了，文档没跟上 |
| 03 的否决项 vs 01 的「不做」清单 | 被否决的方案又出现在设计里 |

**任何一条对不上，先修再交。** 三份互相矛盾的文档，比只有一份更糟——下游不知道该信哪个。
