# 契约细节（L3）

## 六个常见契约（示例，不是教条）

| 契约 | 定义者 | 消费者 | 关键内容 |
|---|---|---|---|
| 世界/领域快照 | 架构 | 所有读状态的模块 | 状态 ID、关键量、可用动作、置信度 |
| 状态/术语词表 | 架构 | 识别层、控制层 | **封闭集合** + 互斥规则 |
| 动作/命令原语 | 架构 | 控制层、执行层 | 原语集合 + 超时语义 |
| 资产/配置格式 | 识别层 | 消费方、热更新 | 版本、阈值、组织方式 |
| 事件/日志 | 架构 | 全部 | 结构化 schema |
| 参数 schema | 架构 | 决策层、运维 | 参数、默认值、单位 |

**"封闭集合"是重点**：词表必须是一个能被签字确认的有限列表。不封闭，并行单元各自往里加，最后没人知道全集。

**每个契约必须有唯一写者。** 这是唯一能防止"热心地各自改接口"的结构性手段。

**减少共享契约的数量不等于省事**：n 个单元两两协商是 **n(n−1)/2** 次，收敛到 k 个共享契约后是 **O(n)**，且新单元加入时不用重谈。**找"最小充分共享集"是这一级的全部工作。**

## 桩：契约要可执行，不只是被声明

只冻结文档**仍然会阻塞**。三个条件缺一不可：

| 条件 | 缺了会怎样 |
|---|---|
| ① 接口窄（契约数量少） | 协商成本回到平方级 |
| ② **桩可执行** | 下游仍要等上游真实实现，只是等得更文明 |
| ③ **每个单元有独立验收夹具** | 无法判断是否完成，只能等集成时发现 |

②③ 才是"不阻塞"的实质：**把"等待别人的产物"换成"对着冻结的桩开发和验收"**。

由此得出可交付单元的定义——**不是"最小工作单元"，而是"最小的、可以被独立验收的单元"**。二者经常差很远。

## 02 永远是索引，不存在"不需要"的档位

三种东西要分开：

| 层 | 是不是必须有 |
|---|---|
| 契约本身（那些约定） | 必须有 |
| 契约的载体 | 代码里的类型 + 02 里的索引行 |
| 02（契约文档） | **永远有**，形态固定为**索引**：形状那一栏指向代码位置 |

「不需要契约文档」这句话不成立——02 永远存在。真正会变的是**约定栏装多少**，由这份契约要表达什么决定：

| 契约里有没有这类东西 | 有就必须写进约定栏 |
|---|---|
| 不变量（行数闭合、金额守恒、状态互斥） | ✅ |
| 封闭集合（错误码、状态枚举、职级） | ✅ |
| 唯一写者 | ✅ |
| 错误码 → 行为的映射 | ✅ |
| 只是一个字段形状 | ❌ 形状栏指过去就够 |

代码里写不下这些，所以它们必须留在 02。**这跟几个人写无关，跟这份契约说了什么有关。**
