# 派发：≥2 条并行线

> **什么时候读**：选片判出可以并行之后、派出之前。

---

## 派之前先冻结

把这一片所有线共同依赖的契约在 02 里标为已冻结（加版本号）。

**没冻结就派 = 两个写者对同一份约定各写各的，合的时候才发现对不上。**

## 任务卡

一张卡 = 一条线 = 一个写者。

```
目标：一句话，可验收
依赖契约：<名称> v<版本>
输入：读哪些文件，精确到节
输出：创建/修改哪些文件；**明确不许碰哪些**
验收：命令 + 期望输出（不是"实现正确"）
边界：不许改契约。发现契约不足 → 停下报告
回滚：失败时怎么干净丢弃
返工理由：（硬字段，发生时必填）理解 / 假设 / 验收不可测 /
          切分丢约束 / 上下文丢失 / 实现跑偏 / 越线
```

**返工理由是硬字段**：卡上留空位，一旦返工就必须填。不用写故事，写清"哪一类 + 一句话"。它不是复盘，是复盘的原料——理由不记，事后就再也拿不到了。

## 星形 DAG：卡之间不许有依赖

每张卡只依赖契约，不依赖其他卡 → 任何顺序都能开工，任何人先完成都不影响别人。

**一旦画出依赖链（B 必须在 A 之后），那就是缺了一个契约。** 如果 B 真的需要 A 的产出，那 A 的产出本应是一个冻结产物（契约、资产、数据文件），而不是运行时依赖。

> 切任务时看到链，先别排顺序，回去找那个缺失的共享物。

## 验：契约符合性检查

每条线交回来，除了跑验收，还要查四样：

1. **卡外文件没被改**——diff 只落在卡里声明的路径
2. **契约没被改**——02 的 diff 只有 `待落地 → 已落地`，没有约定变化
3. **封闭集合没被加值**——错误码、状态枚举都没有新增
4. **唯一写者没变**

任一条不过 → 打回那条线，不许合。

## 合并：一次只合一个

即使并行开发，合并串行。每合一个跑一次冒烟，再合下一个。

两阶段 review，顺序不许反：

1. **规格符合性**——是否只做了卡里的事
2. **代码质量**

先审规格，否则你会先花时间美化一段本来就不该写的代码。

## 冲突裁决

合并冲突不是技术问题，是切片判错了。按这三条判：

| 冲突类型 | 判定 | 动作 |
|---|---|---|
| 两条线改到同一文件 | **切分失败** | 停，把两条线合成一条重做 |
| 一条线改了契约（本不该改） | **越线** | 打回，重跑 |
| 契约本身不足以支撑两条线 | **契约不足** | 停，回 `solution-design` 补契约，两条线都等 |

**不许「谁先合以谁为准」。** 那是让先到者定义规则、后到者返工。
