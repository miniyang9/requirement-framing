# Incremental Delivery（执行）

上游是 `solution-design`，输入是 01 / 02 / 03。
本 skill 把设计变成**一串能独立验收的增量**，每做完一片落一次账。

**它既做串行，也做派发。** 派发不是更高的一档，而是同一步骤在边界切得开时的做法——判据见「选片」。

## 门禁：三件齐 + 已冻 + 已签

1. `docs/arch/<slug>/` 下 01 / 02 / 03 齐，且 01 首行写着 `frame: docs/frame/<slug>.md`
2. 02 开头有冻结行：`冻结：<日期>    冻结人：<角色>`
3. **frame 是已签的**：`状态：已签`，且签字块三字段齐（签字人 / 签字日期 / 版本）。**没有签字的设计不许开工。**
   - 如果它是**增量 frame**（顶部声明了「本文件是 `<path>` 的增量 frame」），**连基线一起读**：基线 + 增量合并，冲突处以增量为准。**收敛和黑盒的验收条数是两边之和**——只算增量那份，会漏掉基线里没被推翻的验收。
4. **要派发时**：本片依赖的那几条契约必须已冻结（有版本号、写者不许改）。没冻结就派发 = 两个人对同一份约定各写各的。

**缺设计产物**（01/02/03、冻结行）→ 退回 `solution-design`；**frame 未签** → 退回 `requirement-framing`。两条路不要合并。设计不全时开工，等于把缺口留给未来的自己。

## 接手已有项目：先补一次 arch 复审

如果 `docs/arch/<slug>/review.md` **不存在**（项目是在这条规则之前开的），**在正式做下一片之前先补一次 arch 复审**。

- 复审对象是**现有的** 01 / 02 / 03 **和 frame**
- 结果写 `docs/arch/<slug>/review.md`，末行 `状态：已关闭（N 轮，阻断 0）`
- 补审发现的问题按「人类裁决之后」那张表处理

**不补，这个项目就永远缺这一次审**——arch 复审的触发点是「骨架收敛后」，那早就过去了。

## 开工前：环境假设要实测

下「环境不支持 X」的结论之前，换**至少两种互不依赖**的手段验一次。一个探针失败，说明的是这个探针，不是环境。

| 想验 | 可靠做法 | 容易误判的做法 |
|---|---|---|
| 有没有网 | `node -e "fetch('https://…').then(r=>console.log(r.status))"` | `curl`——Windows 上走 Schannel，可能与你无关地失败（返回 `000`） |
| 能不能装包 | 项目根写一行 `.npmrc`：`cache=.npm-cache`（缓存必须在工作区内） | 直接 `npm i`——缓存默认在 `%LOCALAPPDATA%`，在工作区外会被沙箱拦成 `EPERM`；也别指望用户级变量，沙箱临时目录每个 session 都变 |
| 能不能跑测试 | 直接跑测试文件 | `node --test`——它 spawn 子进程，被沙箱拦 |

**三个失败信号连着来，很可能一个都不成立。** 把「环境不支持」当成既定事实，代价是去手写本该直接用的东西——真实案例里，为此手写了 191 行 WebSocket，而 `npm install ws` 只要 1 秒。


## 第一次进 C：全面盘点外部依赖

门禁过了之后，**先盘点一次，再选第一片**。只做一次；之后每片只验自己用到的那几项。

1. 读 frame 的 `## 外部依赖`
2. 逐项标：**可用** / 不可用 / 还不能验
3. 不可用的，问清「最晚何时能给」
4. 据此排出「现在能做哪些片」

**「可用」不能采信声明。** 人说"服务器 IP 是 1.2.3.4"，你得真连一次：

| 依赖 | 探针 |
|---|---|
| 服务器 | SSH 或端口连通 **+ 真跑一条命令**，把输出写进状态 |
| 域名 | 解析到预期 IP + HTTPS 能握手 |
| 数据库 | 连一次 + 建表 + 删表 |
| 样例数据 | 真读一次，字段齐不齐 |
| 账号 / API | 真调一次，看返回码 |

盘点结果回写进 frame 那几行的 `状态` 栏（带探针和日期），然后在回复第一段说清：**能做哪些、卡在哪、什么时候解。**

## 不可逆动作之前：先回答「怎么回去」

**不可逆动作**：删 / 批量改生产数据、数据迁移、覆盖线上配置、对外发布（发版、发消息、上线）、给人装东西。

**本地开发环境不算**——那里可以随便毁。

做之前必须回答一个问题，答案写进台账：

> **这一步做错了，怎么回到做之前？**

| # | 答案 | 硬要求 |
|---|---|---|
| 1 | **能回滚** | 备份**验证过能恢复**：在副本上恢复一次，比对行数 / 校验和。**没验证过的备份等于没有** |
| 2 | **能重放** | 操作幂等（跑两遍结果相同），且有对账口径——「源行数 = 目标行数」「金额总和相等」这类 |
| 3 | **能绕开** | 先在影子 / 副本上跑完整一遍，差异为 0 才碰真数据；**分批**：1% → 10% → 100%，每批之间有检查点 |
| 4 | **都不能** | **停**。要么设计一个能回去的办法，要么人逐步确认每一步 |

**选了 3 就必须分批。** 一次性跑 20 万条，中途失败时你不知道停在哪、哪些已生效。

**每批之后要能判定「这批对了没有」**：行数、校验和、抽样比对，任一条能用就行。**判定不了就不准进下一批。**

**结果写进台账，一行**：

```
不可逆：迁移 client 表 20 万行
回去方式：3（影子库全量差异 0 → 分批 1%→10%→100%）
检查点：每批后 源行数=目标行数 且 金额总和相等
```

**没有这一行，不许执行。**

## 核心循环（五步）

```
选片 → 写 → 验 → 收尾 → 收敛判定
```

**一轮只做一片。** 做完一片才允许看下一片。

### 1 选片

判据是**"能被独立验收"**，不是"工作量最小"。

- 一片 = **一次上下文能装完**的量；装不下就再切
- 优先级：先做能证伪设计的（骨架优先），再做补全
- 若 01 写明 L5 合并进第一片，**第一片就是那个骨架**

**切好之后，再判这一片能不能并行。** 问：能不能拆成 2 条以上互不相交、各自可验收的线？

三条同时成立才拆：

1. **路径不相交**——各条改的文件/目录不重叠
2. **各有独立验收判据**——不许「等对方完成才能验」
3. **每片装得进一个上下文**——按读写文件数估过

能 → **先冻结本片依赖的契约**（加版本号），再按 `references/dispatch.md` 派发
不能 → 自己串行做完

判据不是「人够不够」——agent 永远够。是**边界切不切得开**。

不许一次挑两片「顺手一起做」。

**被外部依赖挡住怎么办**

三条同时成立才允许跳过这一片、去做后面的：

1. 缺的是**外部依赖**（服务器、域名、样例数据），不是"前一片还没写"——缺代码依赖说明切片判错了，回选片重切
2. 后面存在**不依赖这一片产出**的片
3. 跳过的**不是 L5 骨架片**——骨架只能等，不能跳。它的作用就是尽早证伪设计

跳 → 台账写 `没做：等 X（最晚 <日期>）`、`下次：X 到位后先做第 N 片`
不跳 → 停下，说明为什么不能跳（通常是没有别的片可做）

**连续跳过要在同一句里报告**：`第 3、4 片被 X/Y 挡住，现在做第 5 片`。不许默默跳到后面——那会让台账看起来进度诡异。

### 2 写

**串行就自己写；派发就按任务卡派**（见 `references/dispatch.md`）。三条规矩对两者都成立：

- **不许改契约**——02 里的唯一写者、封闭集合、不变量。**允许**：写实现、加实现内部字段、把 `待落地` 更新成 `已落地 → 文件:行`
- 契约不足 → **停**，记一笔，回 `solution-design`；不许就地扩字段
- 不许"顺手"加 01 里"不做"清单上的东西
- **写一个非平凡部件之前，先看 `solution-design` 的「造还是用」**——默认自造是模型的偏向，不是判断

### 3 验

跑 01 / 02 里写明的验收判据，**不是"看起来对"**。

- 有 fixture 的跑 fixture
- 有命令的跑命令
- 骨架片：验的是"设计是否成立"，不是"功能是否完整"

**契约要有一条具名测试盯着。** 02 里每个契约至少一条断言覆盖它：唯一写者、封闭集合、不变量各一条，测试名带契约编号（`C5 · 房间列表倒序`）。契约升版本 → 对应测试必改；**测试没改 = 契约改了没人知道**。

**验不过怎么办**

**先记失败集合**，不是记错误文本：`测试名 + 断言位置`。错误文本会因为加一行代码、换个随机种子就变——它不代表进展。

每轮「改 → 跑」后，把这一轮的失败集合和上一轮比：

| 变化 | 判定 | 动作 |
|---|---|---|
| 变小（真子集，且没新增） | **推进** | 继续 |
| 不变 | **原地** | 换一个能被一句话说清的假设，再试 |
| 变大，或出现原来没有的失败 | **倒退** | 停——这轮修错了 |

**停的条件（任一成立）：**

1. **要改 02 里的约定才能让它过**——这不是 bug，是设计缺口 → 回 `solution-design`
2. **同一断言，连续 3 个不同的假设都失败**——你的问题模型错了，不是耐心不够 → 停，把这 3 个假设一字排开写下来，答案往往在里面
3. **失败集合连续 2 轮变大**——边界判错了 → 回 `solution-design`，或回选片重新切

「假设」必须是能被一句话说清的（"我以为房间用 `p0..p3`，其实用 uid"）。说不出新假设，就说明已经不知道该改什么了——那也该停。

**不停的情况**：第一次、第二次失败；失败集合在变小。

**这三个判据里没有「修了多久」和「错误信息变没变」**——这两个都不是客观信号。


### 4 收尾

往 `docs/build/<slug>.md` **追加**：

```
## <片名> · <日期>
做了：
没做：
下次：
证据：<跑过的命令 / fixture / 日志字段，一行结果>
收敛：x/5（缺哪条，写清楚）
返工：无 / <七类之一 + 一句话>
```

**返工理由分七类**（硬字段，发生时必填）：

| 类 | 什么时候填 | 回哪 |
|---|---|---|
| 理解 | 需求里某句读错了，后来才发现 | 回 `requirement-framing`（需求要改写） |
| 假设 | 用了一个没验证的前提 | 就地——把假设变成事实，再验一次 |
| 验收不可测 | 01 的验收判据写不出证据 | 回 `solution-design` |
| 切分丢约束 | 切片时漏了 01/02 的某条约束 | 回选片，重新切 |
| 上下文丢失 | 换了会话，忘了前面定过的约定 | 读台账 + 相关契约重建；**不重做** |
| 实现跑偏 | 代码和设计不符，设计本身没错 | 就地重写那一段 |
| 越线 | 签字前就开工了 | 回 `requirement-framing`，先补签 |

**填了类目就知道下一步去哪**——这张表是判据，不是标签。

**返工理由是硬字段。** 没有它，三个月后你不知道偏差通常发生在哪一跳。

**台账顶部那一行状态，只有三个值：**

| 值 | 什么时候写 |
|---|---|
| `进行中（第 N 片）` | 正常推进 |
| `待交付` | 所有片 5/5，正在走发布闸门 |
| `带残余风险交付` | 人类明确选择在四条件未满足时发布；未满足项已逐条登记 |
| `已交付` | 四条件全过 + 人类确认 |

**「已上线」「已部署」「已发布」不是状态。** 它们是**发布事实**，写在台账正文那一节里。

状态行写「已上线」= **用一次部署冒充一次交付**——两者之间还差着全量黑盒、冒烟、评审结论、人类确认。真实案例：CardGame 的台账写着 `状态：已上线`，而黑盒一次都没做过、交付四条件一条都没走。

**本片让哪个契约落地了？** 有 → 去 `02-contracts.md` 把那一行的 `待落地` 改成 `已落地 → 文件:行`。这是唯一需要动设计文档的时刻，别攒着——攒着就一定会忘。

片级 review 是**代码 review**，不是设计 review——设计已经在 frame 复审和 arch 复审里审过了。

把产物 + 验收结果交给一个**新会话（无前序上下文）**，按三样查：

1. **没多没少**——只做了这一片该做的，没顺手加别的
2. **实现质量**——测试是不是在验规格（不是"看起来对"）、有没有断言放水、有没有"测了 happy path 就算"
3. **没违反契约**——唯一写者、封闭集合、错误码、版本号都守住了

**发现设计问题就停，回 `solution-design` 补契约——不许在代码里绕过。** 片级 review 不许改设计。

**顺序是 review → 台账，不是反过来。** 反过来，台账记的是"我做了什么"，而不是"别人验过什么"。review 的结论和证据写进那一行 `证据：`。
### 5 收敛判定

**每片收尾都要重跑，不是只在最后跑一次。** 结果写进这一片的 `收敛：x/5` 行——不要另开一节记录收敛状态，那种快照一定会过期。

五项收敛检查（它们和 01 的五个架构问题不是一回事）：

- **frame 里每条验收标准都有对应证据**（命令 / fixture / 日志字段）？——这是需求级，缺了后面几条都白打。**有增量 frame 时，基线 + 增量的验收全都算**
- 01 的五问各有对应代码 + 证据？
- 02 的每个契约都有唯一写者，且代码里属实？
- **02 里的 `待落地` 是否都已变成 `已落地 → 文件:行`？**（指针过期 = 文档在说谎）
- 01 的"不做"清单，一条都没被违反？

缺口 → 回 `solution-design` 补设计（不回 `requirement-framing`，也不就地改）。

**有被跳过的片 → 直接判不能交付**，不用再算五项——台账里那条 `等 X` 本身就是缺口。

**所有片都 5/5 之后 → 进「发布闸门」，不是直接写交付。** 黑盒是那一步的事，不在每片里。

## 发布闸门：黑盒 → 发布 → 冒烟 → 人确认

**黑盒不是每片的动作，是发布前的一道闸门。**

每片做的是：写、验（测试套件）、片级 code review、收敛。**黑盒发生在「准备把这东西交给外部使用」那一刻**——它问的是「从外面看，这个整体能不能用」，而片还没做完时，外面看到的本来就不完整。

四步，顺序不能变。**每次发布都走一遍；只有最后一次带交付。**

### ① 全量黑盒（阶段一 · 工作区）

**用例集是累积的一份**，跟着已交付的能力长——没做的功能不写用例。交付前跑全量。

角色两个，有先后：设计员写用例 → 评审员审用例（**这是门**）→ 设计员执行 → 评审员完整评审。

**设计员：新 subagent，只写用例，不执行。**

给它**只有两样**：frame（§7 验收 + 范围方案）+ 一条能把它跑起来的命令。**不给代码、不给你的实现思路、不给对话历史。**

给了就是白盒——**照着实现写的用例，永远会通过**。写用例的人必须只知道"这东西应该做到什么"，不知道"它是怎么做的"。

产出 `docs/build/<slug>.blackbox.md`。每条：编号 / **环境** / 维度 / 前置 / 步骤 / **可判定的期望** / 怎么收集证据。

`环境` 只能填 `本地` 或 `生产`。**生产组里不许出现破坏性用例**（删数据、并发压测、注入故障）——那些只能在本地做。

期望必须可判定：「正常显示」不行，「返回 3 条、按创建时间倒序、第一条 id=7」才行。

**七维——任何项目都过一遍，每维必须落成本项目自己的可观察量：**

| # | 维度 | 问的是 |
|---|---|---|
| 1 | **功能完备** | 该做的都做了吗？边界输入、空输入、非法输入呢？ |
| 2 | **性能** | 在**指定的负载下**，时间和资源够用吗？ |
| 3 | **兼容共存** | 和目标环境、和同时装着的别的东西放在一起，还正常吗？ |
| 4 | **可靠与可恢复** | 连续跑得稳吗？出事后能恢复吗？状态会不会丢？ |
| 5 | **交互** | 状态看得见吗？能反悔吗？错误能懂能救吗？说人话吗？ |
| 6 | **安全边界** | 看不到不该看的吗？越权会怎样？ |
| 7 | **灵活性** | 换环境、换配置、量变大，还成立吗？ |

（取自 ISO/IEC 25010:2023 的八项产品质量特性，去掉白盒的可维护性；交互那维并入 Nielsen 十项。明示排除：审美、情绪、认知负荷——只能人测。）

**写不出指标的那一维，标「未覆盖，需人类」。** 不许用「体验良好」「交互流畅」糊过去。

**评审员：审用例集——这是门，不过不许执行。** 新 subagent，给用例集 + frame，**不给代码**。

1. 七维都覆盖了吗？缺的有没有写明为什么
2. 全是 happy path 吗？边界 / 非法输入 / 异常状态 / 重复与并发有没有
3. 每条期望可判定吗？有没有「正常」「友好」「流畅」混进来
4. 每条说清怎么收集证据了吗
5. **生产组是不是只读 / 可回滚？** 有没有混进破坏性用例

不过 → 改 → 再审（最多 2 轮）→ 仍不过 → 交人。

**过审后冻结用例集。** 执行段只能追加结果，**不许改期望**——「改期望让它通过」是最自然的下意识动作。

**执行：** 按冻结用例跑 `环境=本地` 那组，证据必须可核对。

**本地不全绿，部署命令一行都不许敲。**

### ② 发布（推到它将要运行的地方）

**发布 ≠ 片。** 片是一块可独立验收的能力；发布是一次把产物推到运行环境的操作。**片里不出现「部署」这个交付单元**——「部署上线」不是一片。

| 项目 | 发布是什么 | 冒烟是什么 |
|---|---|---|
| Web 服务 | 推到服务器 | healthz / 证书链 / 登录一次 |
| 本地工具（如 CoC） | 装到用户的机器上 | 在真实窗口跑一次（通常是人代） |
| 定时任务 | 注册到真实调度器 | 等它真跑一次 |
| CLI | 装到用户的 shell | 用真实文件跑一次 |
| 纯库 / 纯算法 | **不适用** → 写明理由 | — |

**发布可以发生多次**，而且应该：

```
发布 #1（骨架）：全量黑盒（只有骨架的用例）→ 发布 → 冒烟 → 不交付
发布 #2（全功能）：全量黑盒（全量用例）→ 发布 → 冒烟 → 评审 → 交付
```

这也是 B 那条「骨架要接真实环境」的实现方式——**靠提前发一次，不是把部署做成一片**。

**这是不可逆动作**——先按「不可逆动作之前」那一节回答「怎么回去」，答案写进台账。

**阶段一全绿是前置条件，不是建议。**

### ③ 冒烟（阶段二 · 真实环境）

跑 `环境=生产` 那组（对纯库来说这组为空，写明理由）。**每次发布都跑，不是只跑一次**——部署回归是最容易漏的一类：本地全绿、上机就挂。

- 只读或可回滚：不造真实数据、不压测、不注入故障
- 冒烟至少覆盖：服务在、端口对、证书链能过、登录和核心路径各走一次
- **跑挂了 → 回滚**，不是就地改代码

**做不到怎么办**（要真机、要浏览器、要硬件，agent 没有手）：

1. **先枚举可用工具**——不是「找找看」，是列出来：我的工具列表里有什么？能不能做串口 / 鼠标 / 浏览器？没有的话有没有现成的 MCP 能装？
2. **数一下有多少条用例需要它**：只有 1 条 / 只这一次 → **直接人代，不问**；≥2 条或反复用 → **停下来问一次**（装 MCP 还是这次先人代）。写一行「工具判断：…」进 blackbox.md，**数不出来 = 没判过**。
3. 工具也没有 → **人代执行**，按 `references/human-executed-testing.md` 的协议。人只说「没问题」没给证据 → 记**未验证**，不算通过；人拒绝 → 记 `未覆盖（人拒绝执行：原因）`，项目不因此卡死。
4. **「不装」不是错，「默默人代」才是错。** 同一类测试已经人代过两次、第三次还不问，就是在消耗人。

**每次人代执行做完，如果 `references/cases/` 里没有这一类任务，补一篇。**

### ④ 评审员完整评审，给发布结论

新 subagent，**逐条核**，不是抽检。本地组和生产组都要核：

```
结论：可发布 / 不可发布
依据：本地 N 条全绿；生产 M 条全绿；未覆盖 K 项（已列明）
问题：<用例编号> + 为什么 + 建议
```

**跑不起来 → 停，报「无法黑盒」。** 不许拿读文档的推断冒充测试结果。

**结论「可发布」+ 交付四条件全过 → 才能写交付。**

### 交付：四个条件，缺一不可

1. **所有片 `收敛：5/5`**——有被跳过的片 → 不满足
2. **两个阶段都全绿**：阶段一（本地全量）+ 阶段二（生产冒烟），没有未闭环的问题
3. **测试评审员的结论是「可发布」**
4. **人类明确认可**——把 ①–④ 的结果交给人，他说可以，才写交付

前三条机器能给，**第四条只能人给**。

**四条件只是「干净交付」那一条路。** 人类可以在不满足它们的情况下发布——但那要写 `带残余风险交付`，不是 `已交付`。

**「已交付」必须四条全过**，否则这个词就不携带任何信息：读台账的人分不出这是干净交付还是强行发布。

**状态流转**：

```
进行中 → 待交付（进发布闸门时转）→ 已交付（四条件全过 + 你认可）
```

**人类不认可 → 按缺口类型回**：代码缺陷回那一片重做；设计缺口回 `solution-design`；需求变了回 `requirement-framing`；用例本身不够 → 回 ① 补用例重走。

然后才写：

```
## 交付 · <日期>
范围：<frame 的范围方案>
依据：第 N 片 `收敛：5/5`；黑盒 <N> 条全绿；评审结论：可发布（<日期>）
偏离：<frame 的 `## 偏离` 节里本项目相关的行，逐条列出；没有就写 无>
已知风险：<从 03 的 ADR 汇总那些标了「已知风险」的依赖，没有就写 无>
人类确认：<姓名 / 日期>
未做：<明确列出的没做项，没有就写 无>
```

**这一节只能在状态变成 `已交付` 之后写，且必须引用最后一次收敛行。**
没有引用 = 不算交付，只是聊天里的一句话。

> **串行与派发在每一环的差别** → 读 `references/workmode.md`。选片之前必读。

## 骨架收敛后：arch 复审（只做一次）

**第一片（骨架）收敛之后、第二片开工之前**，对 01/02/03 做一次对抗性复审。

**为什么在这**：B 只给骨架的判据，骨架是这里跑出来的。**在骨架跑之前审设计，等于在没做实验之前审实验报告。**

**谁审**：新 subagent，只给四条路径（01 / 02 / 03 / frame）+ 下面清单。**不给你的思路、不给对话历史、不给"重点看哪里"。**

**审十一项：**

1. **五个问题**：每问给的是"选了哪个、为什么"，还是写成了教程？
2. **契约**：每条有唯一写者？约定栏装的是代码表达不了的东西（不变量 / 封闭集合 / 错误码）？形状栏还写着"待落地"但其实已经能指向代码了吗？
3. **决策**：每条有"否决了什么"？改过的决策有没有连带改 01？
4. **验收**：frame 的每条验收标准都有对应证据？L2 五问各有证据？证据是命令 / 夹具 / 日志字段，不是"已验证"？
5. **落盘形状**：目录树 + 每个产物落在哪？
6. **骨架判据**：每条有阈值（数字或布尔）？它真能证伪设计，还是只是"跑通了"？
7. **图**：每张图有源 + 渲染器 + 命令三件齐？
8. **交叉一致**：01 的契约清单 ↔ 02 的索引 ↔ 03 的 ADR 能对上吗？有没有"01 说做了、03 说否决了"？
9. **骨架实测 vs 01 的判据**：01 说骨架会验出什么，实际跑出来是什么？对不上 → 要么改 01，要么说明设计既没被证伪也没被证实。
10. **执行期发现有没有回写**：跑骨架时发现的契约不足 / 边界错，写进 02/03 了吗？还是只改了代码？
11. **对 frame**：01/02 的假设还对得上 frame 的 §0 和 §4 吗？有没有承重事实被推翻、决策点被改写，却没回 L1 重签的？（真实案例：部署从「境外 + 域名」改成「大陆纯 IP + 自签」，只写了一条 ADR，frame 里十二处仍是旧口径，其中一条承重事实已经失效。）

第 9、10 项是「在骨架之后审」的价值；第 11 项是**回去对签字的那份需求**——设计可以变，但变了就得有人重新签字。

**记在哪**：`docs/arch/<slug>/review.md`（和 01–03 同目录，**不编号**，免得被当成第四份设计）。末行必须有状态：

```
状态：已关闭（2 轮，阻断 0）
```

或

```
状态：未闭环（阻断 1，已交人裁决）
```

**轮次**：R1 → R2（必触发）→ R3（仅当 R2 留阻断，**只核不找**）。每轮换新 subagent。每轮阻断数必须下降。

- **关闭 → 继续第二片。**
- **未闭环 → 停，交人裁决。**

## 人类裁决之后

| 裁决 | 动作 | 记在哪 | 复审 |
|---|---|---|---|
| **A. 接受现状**（带着风险走） | 继续往下 | **03 记一条 ADR**：`否决：<R编号>，理由…` | 不重开 |
| **B. 问题成立，改文档** | 回对应级改 | review.md 的裁决节 | **重开**（R1 重计，已裁决项不重复） |
| **C. 问题指向设计本身错了** | 回 `solution-design` 重做 01/02/03 | review.md | 重开 |
| **D. 问题指向需求没想清** | 回 `requirement-framing` 改 frame、重签 | review.md + frame | 重开 |

**A 也必须留痕，而且不能只留在 review.md 里。** 接受现状的阻断项是永久风险，而未来的人只看 01/02/03，不会翻 review.md——所以必须进 03 的 ADR。

**重开有界**：同一份文档重开 **2 次**仍无法关闭 → 不再重开，建议回上一级重做。打磨文档解决不了的问题，通常不是文档的问题。

**不许「你看着办」**：允许授权 AI 裁决，但必须在 review.md 写明性质：

```
- R2-3 [阻断] → 授权 AI 代为裁决：采纳否决，理由……
  （签字人：… ；性质：授权裁决，非本人判断）
```

**骨架代码的连带处理**：裁决导致 01/02/03 改了结构（分层、契约数量、边界）→ **骨架代码作废，重做第一片**；只改措辞或补证据 → 代码不动。设计变了，那条最薄路径就不再证明任何东西。

## 什么时候停

收敛 5/5 之后，看三样：

1. **还有剩余片，且没有阻塞 → 继续下一片，不要停下来问**
2. **被外部依赖挡住且无片可做** → 停，说明在等什么
3. **需要人类决策** → 停，问清楚；**拿到答案后回到刚才那一片做完，再往下走**

只有「交付完成」、或者第 2、3 条，才是合法的停。

**「一次一片」是节奏，不是收工信号。** 它说的是不许并行、不许顺手多做一片，不是"做完一片就结束这一轮"。台账顶部的 `状态：进行中（下一片：…）` 写着还有活，就接着做。

## 铁律

- **执行中不改「约定」，只更新「指针」。** 唯一写者 / 封闭集合 / 不变量——不许动；`待落地 → 已落地`——每片必更。缺口回 `solution-design`；需求变了回 `requirement-framing`。
- **一次一片。** 两片并行，等于两片都没验。
- **依赖缺了先绕后等。** 骨架片不饶；缺代码依赖不许绕（那是切片错）。
- **改 frame 覆盖过的东西 = 改需求。** frame 的 §0 承重事实 / §4 决策点里有的，不许在这里或 03 里「覆盖」——回 `requirement-framing` 重签。**ADR 里写出「覆盖 frame」就是越线信号。**
- **收敛每片重跑，写进这一片。** 不写独立章节——独立章节是快照，一定会和事实脱钩。
- **收尾必写返工理由。** 没有返工也要写"无"。
