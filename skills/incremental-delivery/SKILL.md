# Incremental Delivery（执行）

上游是 `solution-design`，输入是 01 / 02 / 03。
本 skill 把设计变成**一串能独立验收的增量**，每做完一片落一次账。

**它既做串行，也做派发。** 派发不是更高的一档，而是同一步骤在边界切得开时的做法——判据见「选片」。

## 门禁：三件齐 + 已冻 + 已签

1. `docs/arch/<slug>/` 下 01 / 02 / 03 齐，且 01 首行写着 `frame: docs/frame/<slug>.md`
2. 02 开头有冻结行：`冻结：<日期>    冻结人：<角色>`
3. **frame 是已签的**：`状态：已签`，且签字块三字段齐（签字人 / 签字日期 / 版本）。**没有签字的设计不许开工。**
4. **要派发时**：本片依赖的那几条契约必须已冻结（有版本号、写者不许改）。没冻结就派发 = 两个人对同一份约定各写各的。

**缺设计产物**（01/02/03、冻结行）→ 退回 `solution-design`；**frame 未签** → 退回 `requirement-framing`。两条路不要合并。设计不全时开工，等于把缺口留给未来的自己。

## 开工前：环境假设要实测

下「环境不支持 X」的结论之前，换**至少两种互不依赖**的手段验一次。一个探针失败，说明的是这个探针，不是环境。

| 想验 | 可靠做法 | 容易误判的做法 |
|---|---|---|
| 有没有网 | `node -e "fetch('https://…').then(r=>console.log(r.status))"` | `curl`——Windows 上走 Schannel，可能与你无关地失败（返回 `000`） |
| 能不能装包 | 项目根写一行 `.npmrc`：`cache=.npm-cache`（缓存必须在工作区内） | 直接 `npm i`——缓存默认在 `%LOCALAPPDATA%`，在工作区外会被沙箱拦成 `EPERM`；也别指望用户级变量，沙箱临时目录每个 session 都变 |
| 能不能跑测试 | 直接跑测试文件 | `node --test`——它 spawn 子进程，被沙箱拦 |

**三个失败信号连着来，很可能一个都不成立。** 把「环境不支持」当成既定事实，代价是去手写本该直接用的东西——真实案例里，为此手写了 191 行 WebSocket，而 `npm install ws` 只要 1 秒。


## 第一次进 C：全面盘点外部依赖

门禁过了之后，**先盘点一次，再选第一片**。只做一次；之后每片只验自己用到的那几项。

1. 读 frame 的 `## 外部依赖`
2. 逐项标：**可用** / 不可用 / 还不能验
3. 不可用的，问清「最晚何时能给」
4. 据此排出「现在能做哪些片」

**「可用」不能采信声明。** 人说"服务器 IP 是 1.2.3.4"，你得真连一次：

| 依赖 | 探针 |
|---|---|
| 服务器 | SSH 或端口连通 **+ 真跑一条命令**，把输出写进状态 |
| 域名 | 解析到预期 IP + HTTPS 能握手 |
| 数据库 | 连一次 + 建表 + 删表 |
| 样例数据 | 真读一次，字段齐不齐 |
| 账号 / API | 真调一次，看返回码 |

盘点结果回写进 frame 那几行的 `状态` 栏（带探针和日期），然后在回复第一段说清：**能做哪些、卡在哪、什么时候解。**

## 核心循环（五步）

```
选片 → 写 → 验 → 收尾 → 收敛判定
```

**一轮只做一片。** 做完一片才允许看下一片。

### 1 选片

判据是**"能被独立验收"**，不是"工作量最小"。

- 一片 = **一次上下文能装完**的量；装不下就再切
- 优先级：先做能证伪设计的（骨架优先），再做补全
- 若 01 写明 L5 合并进第一片，**第一片就是那个骨架**

**切好之后，再判这一片能不能并行。** 问：能不能拆成 2 条以上互不相交、各自可验收的线？

三条同时成立才拆：

1. **路径不相交**——各条改的文件/目录不重叠
2. **各有独立验收判据**——不许「等对方完成才能验」
3. **每片装得进一个上下文**——按读写文件数估过

能 → **先冻结本片依赖的契约**（加版本号），再按 `references/dispatch.md` 派发
不能 → 自己串行做完

判据不是「人够不够」——agent 永远够。是**边界切不切得开**。

不许一次挑两片「顺手一起做」。

**被外部依赖挡住怎么办**

三条同时成立才允许跳过这一片、去做后面的：

1. 缺的是**外部依赖**（服务器、域名、样例数据），不是"前一片还没写"——缺代码依赖说明切片判错了，回选片重切
2. 后面存在**不依赖这一片产出**的片
3. 跳过的**不是 L5 骨架片**——骨架只能等，不能跳。它的作用就是尽早证伪设计

跳 → 台账写 `没做：等 X（最晚 <日期>）`、`下次：X 到位后先做第 N 片`
不跳 → 停下，说明为什么不能跳（通常是没有别的片可做）

**连续跳过要在同一句里报告**：`第 3、4 片被 X/Y 挡住，现在做第 5 片`。不许默默跳到后面——那会让台账看起来进度诡异。

### 2 写

**串行就自己写；派发就按任务卡派**（见 `references/dispatch.md`）。三条规矩对两者都成立：

- **不许改契约**——02 里的唯一写者、封闭集合、不变量。**允许**：写实现、加实现内部字段、把 `待落地` 更新成 `已落地 → 文件:行`
- 契约不足 → **停**，记一笔，回 `solution-design`；不许就地扩字段
- 不许"顺手"加 01 里"不做"清单上的东西

### 3 验

跑 01 / 02 里写明的验收判据，**不是"看起来对"**。

- 有 fixture 的跑 fixture
- 有命令的跑命令
- 骨架片：验的是"设计是否成立"，不是"功能是否完整"

**验不过怎么办**

**先记失败集合**，不是记错误文本：`测试名 + 断言位置`。错误文本会因为加一行代码、换个随机种子就变——它不代表进展。

每轮「改 → 跑」后，把这一轮的失败集合和上一轮比：

| 变化 | 判定 | 动作 |
|---|---|---|
| 变小（真子集，且没新增） | **推进** | 继续 |
| 不变 | **原地** | 换一个能被一句话说清的假设，再试 |
| 变大，或出现原来没有的失败 | **倒退** | 停——这轮修错了 |

**停的条件（任一成立）：**

1. **要改 02 里的约定才能让它过**——这不是 bug，是设计缺口 → 回 `solution-design`
2. **同一断言，连续 3 个不同的假设都失败**——你的问题模型错了，不是耐心不够 → 停，把这 3 个假设一字排开写下来，答案往往在里面
3. **失败集合连续 2 轮变大**——边界判错了 → 回 `solution-design`，或回选片重新切

「假设」必须是能被一句话说清的（"我以为房间用 `p0..p3`，其实用 uid"）。说不出新假设，就说明已经不知道该改什么了——那也该停。

**不停的情况**：第一次、第二次失败；失败集合在变小。

**这三个判据里没有「修了多久」和「错误信息变没变」**——这两个都不是客观信号。


### 4 收尾

往 `docs/build/<slug>.md` **追加**：

```
## <片名> · <日期>
做了：
没做：
下次：
证据：<跑过的命令 / fixture / 日志字段，一行结果>
收敛：x/5（缺哪条，写清楚）
返工：无 / <七类之一 + 一句话>
```

**返工理由分七类**（硬字段，发生时必填）：

| 类 | 什么时候填 | 回哪 |
|---|---|---|
| 理解 | 需求里某句读错了，后来才发现 | 回 `requirement-framing`（需求要改写） |
| 假设 | 用了一个没验证的前提 | 就地——把假设变成事实，再验一次 |
| 验收不可测 | 01 的验收判据写不出证据 | 回 `solution-design` |
| 切分丢约束 | 切片时漏了 01/02 的某条约束 | 回选片，重新切 |
| 上下文丢失 | 换了会话，忘了前面定过的约定 | 读台账 + 相关契约重建；**不重做** |
| 实现跑偏 | 代码和设计不符，设计本身没错 | 就地重写那一段 |
| 越线 | 签字前就开工了 | 回 `requirement-framing`，先补签 |

**填了类目就知道下一步去哪**——这张表是判据，不是标签。

**返工理由是硬字段。** 没有它，三个月后你不知道偏差通常发生在哪一跳。

**台账顶部有一行状态**：`状态：进行中（第 N 片）`。每片开工前先更新它；全部收敛后改 `状态：已交付`。

**本片让哪个契约落地了？** 有 → 去 `02-contracts.md` 把那一行的 `待落地` 改成 `已落地 → 文件:行`。这是唯一需要动设计文档的时刻，别攒着——攒着就一定会忘。

串行时的 review 就在这一步：把产物 + 验收结果交给一个**新会话（无前序上下文）**，只问「满足规格吗？哪里不对？」

**顺序是 review → 台账，不是反过来。** 反过来，台账记的是"我做了什么"，而不是"别人验过什么"。review 的结论和证据写进那一行 `证据：`。

### 5 收敛判定

**每片收尾都要重跑，不是只在最后跑一次。** 结果写进这一片的 `收敛：x/5` 行——不要另开一节记录收敛状态，那种快照一定会过期。

五项收敛检查（它们和 01 的五个架构问题不是一回事）：

- **frame 里每条验收标准都有对应证据**（命令 / fixture / 日志字段）？——这是需求级，缺了后面几条都白打
- 01 的五问各有对应代码 + 证据？
- 02 的每个契约都有唯一写者，且代码里属实？
- **02 里的 `待落地` 是否都已变成 `已落地 → 文件:行`？**（指针过期 = 文档在说谎）
- 01 的"不做"清单，一条都没被违反？

缺口 → 回 `solution-design` 补设计（不回 `requirement-framing`，也不就地改）。

**有被跳过的片 → 直接判不能交付**，不用再算五项——台账里那条 `等 X` 本身就是缺口。

**五项全过 → 先把台账顶部的状态改成 `已交付`，再在末尾写一节：**

```
## 交付 · <日期>
范围：<frame 的范围方案>
依据：第 N 片的 `收敛：5/5`
未做：<明确列出的没做项，没有就写 无>
```

**这一节只能在状态变成 `已交付` 之后写，且必须引用最后一次收敛行。**
没有引用 = 不算交付，只是聊天里的一句话。

> **串行与派发在每一环的差别** → 读 `references/workmode.md`。选片之前必读。

## 骨架收敛后：arch 复审（只做一次）

**第一片（骨架）收敛之后、第二片开工之前**，对 01/02/03 做一次对抗性复审。

**为什么在这**：B 只给骨架的判据，骨架是这里跑出来的。**在骨架跑之前审设计，等于在没做实验之前审实验报告。**

**谁审**：新 subagent，只给四条路径（01 / 02 / 03 / frame）+ 下面清单。**不给你的思路、不给对话历史、不给"重点看哪里"。**

**审十项：**

1. **五个问题**：每问给的是"选了哪个、为什么"，还是写成了教程？
2. **契约**：每条有唯一写者？约定栏装的是代码表达不了的东西（不变量 / 封闭集合 / 错误码）？形状栏还写着"待落地"但其实已经能指向代码了吗？
3. **决策**：每条有"否决了什么"？改过的决策有没有连带改 01？
4. **验收**：frame 的每条验收标准都有对应证据？L2 五问各有证据？证据是命令 / 夹具 / 日志字段，不是"已验证"？
5. **落盘形状**：目录树 + 每个产物落在哪？
6. **骨架判据**：每条有阈值（数字或布尔）？它真能证伪设计，还是只是"跑通了"？
7. **图**：每张图有源 + 渲染器 + 命令三件齐？
8. **交叉一致**：01 的契约清单 ↔ 02 的索引 ↔ 03 的 ADR 能对上吗？有没有"01 说做了、03 说否决了"？
9. **骨架实测 vs 01 的判据**：01 说骨架会验出什么，实际跑出来是什么？对不上 → 要么改 01，要么说明设计既没被证伪也没被证实。
10. **执行期发现有没有回写**：跑骨架时发现的契约不足 / 边界错，写进 02/03 了吗？还是只改了代码？

第 9、10 项是"在骨架之后审"的全部价值——它把文档审阅变成了设计验证。

**记在哪**：`docs/arch/<slug>/review.md`（和 01–03 同目录，**不编号**，免得被当成第四份设计）。末行必须有状态：

```
状态：已关闭（2 轮，阻断 0）
```

或

```
状态：未闭环（阻断 1，已交人裁决）
```

**轮次**：R1 → R2（必触发）→ R3（仅当 R2 留阻断，**只核不找**）。每轮换新 subagent。每轮阻断数必须下降。

- **关闭 → 继续第二片。**
- **未闭环 → 停，交人裁决。**

## 人类裁决之后

| 裁决 | 动作 | 记在哪 | 复审 |
|---|---|---|---|
| **A. 接受现状**（带着风险走） | 继续往下 | **03 记一条 ADR**：`否决：<R编号>，理由…` | 不重开 |
| **B. 问题成立，改文档** | 回对应级改 | review.md 的裁决节 | **重开**（R1 重计，已裁决项不重复） |
| **C. 问题指向设计本身错了** | 回 `solution-design` 重做 01/02/03 | review.md | 重开 |
| **D. 问题指向需求没想清** | 回 `requirement-framing` 改 frame、重签 | review.md + frame | 重开 |

**A 也必须留痕，而且不能只留在 review.md 里。** 接受现状的阻断项是永久风险，而未来的人只看 01/02/03，不会翻 review.md——所以必须进 03 的 ADR。

**重开有界**：同一份文档重开 **2 次**仍无法关闭 → 不再重开，建议回上一级重做。打磨文档解决不了的问题，通常不是文档的问题。

**不许「你看着办」**：允许授权 AI 裁决，但必须在 review.md 写明性质：

```
- R2-3 [阻断] → 授权 AI 代为裁决：采纳否决，理由……
  （签字人：… ；性质：授权裁决，非本人判断）
```

**骨架代码的连带处理**：裁决导致 01/02/03 改了结构（分层、契约数量、边界）→ **骨架代码作废，重做第一片**；只改措辞或补证据 → 代码不动。设计变了，那条最薄路径就不再证明任何东西。

## 什么时候停

收敛 5/5 之后，看三样：

1. **还有剩余片，且没有阻塞 → 继续下一片，不要停下来问**
2. **被外部依赖挡住且无片可做** → 停，说明在等什么
3. **需要人类决策** → 停，问清楚；**拿到答案后回到刚才那一片做完，再往下走**

只有「交付完成」、或者第 2、3 条，才是合法的停。

**「一次一片」是节奏，不是收工信号。** 它说的是不许并行、不许顺手多做一片，不是"做完一片就结束这一轮"。台账顶部的 `状态：进行中（下一片：…）` 写着还有活，就接着做。

## 铁律

- **执行中不改「约定」，只更新「指针」。** 唯一写者 / 封闭集合 / 不变量——不许动；`待落地 → 已落地`——每片必更。缺口回 `solution-design`；需求变了回 `requirement-framing`。
- **一次一片。** 两片并行，等于两片都没验。
- **依赖缺了先绕后等。** 骨架片不饶；缺代码依赖不许绕（那是切片错）。
- **收敛每片重跑，写进这一片。** 不写独立章节——独立章节是快照，一定会和事实脱钩。
- **收尾必写返工理由。** 没有返工也要写"无"。

## 红旗

| 你正在想的 | 现实 |
|---|---|
| "契约差一个字段，先加上再说" | 那就是设计缺口，回 `solution-design` |
| "这两片一起做更快" | 两片并行，等于两片都没验 |
| "跑通了就是验收通过" | 跑通 ≠ 符合规格；对 01 逐条打勾才算 |
| "返工理由回头再补" | 回头补的都不是理由，是合理化 |
