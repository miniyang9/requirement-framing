# Requirement Framing

把一个"种子"变成可审查的规格——**在任何人开始拆任务之前**。

## 三条信条

1. **输入是种子，不是规格。** 用户那几句话说的是"什么事、大概什么形状"，不是可验证的东西。默认动作不是补全它，而是展开它。
2. **先展开，后提问。** 先走清单，把"你知道但用户没说"的倒出来；再只问自己判断不了的。先问问题，等于让用户替你做功课。
3. **展开的产物在形态上不能是任务列表。** 只要产物是列表，模型就会一路收敛到底。展开的产物必须是**带状态的判定**。

## 门禁

- 没有通过的 frame 文档 → 不许 plan、不许切任务、不许写代码。
- 展开阶段出现任务列表 → 本轮作废，重来。

## 第 0 步：分流（先算流程税）

| 输入长什么样 | 档 | 走哪些级 |
|---|---|---|
| 一句话已指定单点修改（"把图标改成矢车菊蓝"） | **T0** | 直接做，说一句你做了什么。**不启动本流程** |
| 一句话描述了一个可独立验证的功能，且 <1 天 | **T1** | 只走 L1 的"一页五问" → 直接做。跳过 L2–L7 |
| 一句话描述了一个工程 / 系统 / 平台 | **T2** | 全流程 L1–L7 |
| 已经在拆任务，或要求派发给多个 agent | **T2** | 全流程，**先回退到 L1** |

**必须显式输出一行档位判定**，例如："档位：T1，因为单产物、<1 天、失败可承受、无需并行。" 不写这句，档位会默认滑向 T2。

**成本不在 L1，在 L2–L5。** L1 无论大小都要走（T1 约半小时到一小时）；真正压死小活的是"必须先出架构和契约"。所以：

- T1 的 L1 = 一页五问（体量 / 验收 / 不做 / **最大歧义** / 失败怎么办）
- T1 **只走** 5 问，不逐项走 17 项横切面。这是刻意的减配，不是遗漏
- T1 的唯一硬要求是：**最大歧义必须在动手前解掉**，因为那是唯一会让你做错东西的地方

## 第 1 步：L1 立项展开（六件套）

产出 `docs/frame/<slug>.md`。**本轮禁止输出任务列表、文件路径、实现步骤、代码。**

1. **体量判定** — 分档 + 依据 + "判断错一档的后果"（判小会怎样、判大会怎样）
2. **隐含工作包** — 必须做 / 可能要做 / 建议不做。每条标 `[推断]`（我补的）或 `[你说过]`
3. **横切面覆盖** — 读 `references/cross-sections.md`，逐项给 `已有 / 待定（取决于什么）/ 不适用（为什么）`。**不许合并、不许跳过、不许写成散文。**
4. **决策点** — 选项 / 推荐 / 可逆性 / 晚定代价。按"晚定代价"降序
5. **三种规模方案** — 最小可用 / 正规 / 平台化。各自**放弃什么、锁死什么**（只给放弃项的方案是假方案）
6. **失败预演** — 三个死法 + 最早信号 + 对策

末尾：**最多 5 个问题**，按"影响 × 不确定度"排序，每题带推荐答案。

**自检**：如果横切面 17 项全都"很重要"，说明在写套话。真实系统里一定有若干项应当判"不适用"。

## 第 2 步：人审与收缩

交给用户，只要他做四件事：划掉不适用的、纠正 `[推断]`、回答 5 问、选规模。

**在用户回复前不要进第 3 步。** 这一步的产出是"签字"，不是"同意"。

## 第 3–7 步：按档位展开

先定档，读 `references/modes.md` 的对照表。

| 级 | S 档（单人 / 单 agent） | M 档（多人 / 多 agent） |
|---|---|---|
| L2 架构 | 一页图，能画在一屏内 | 分层、数据所有权、失败隔离 |
| L3 契约 | **写在代码里的类型** | 契约文档 + 版本号 + 唯一写者 |
| L4 决策 | 四行决策日志 | ADR（含被否决的替代方案） |
| L5 骨架 | 最薄的**垂直切片** | 端到端**空壳**，接口全通 |
| L6 切片 | 粒度 = 一次上下文窗口 | 任务卡 + **星形**依赖 DAG |
| L7 节奏 | 每片五步仪式 | 派发 + 两阶段 review |

契约与切片的细则见 `references/contracts.md`。

两档共同的硬约束：

- **L3 每个契约必须有一个唯一写者**，其余只读。
- **L5 骨架是 L2/L3 的验收测试**，不是实现的开始。骨架跑不通 → 回 L2/L3，不是往下走。
- **切任务时看到依赖链，先别排顺序**——链意味着某个该冻结的东西留在了运行时，回去找它。

## 铁律

**M 档**：

> 任务卡里发现契约不足：**停下来报告，不许自行扩展契约。**

并行子 agent 的头号失败模式不是做错，是热心地各自改接口。

**S 档**：

> 任何在上下文重置后还需要知道的东西，必须落盘。

每片收尾写四行：做了什么 / 没做什么 / 下次从哪开始 / **返工理由（发生时必填）**。返工理由只记分类，不写故事。

## 红旗自省

| 你正在想的 | 现实 |
|---|---|
| "先把最容易做的验证一下" | 你冻结错了层。先问它属于哪一级 |
| "架构等写完再补" | 架构不是细化，它是并行的前提 |
| "用户已经说清楚了" | 一句话能说清的只有单点修改 |
| "我先把默认值填上" | 好，但必须**说出来**。没说出口的默认值等于剥夺了用户否决它的机会 |
| "这就是几个独立任务" | 那你应该能画出星形 DAG。画不出来就是缺契约 |
| "先给个方案让他看" | 一个方案是替他选；三个方案才是让他选 |
| "先把代码骨架搭起来" | 骨架的产出必须是"架构是否成立"这个判断，不是功能 |

## 与现有方法的关系

- L1 ↔ BMAD 的 brief/PRD 层、OpenSpec 的 `explore`（"never writes code"）
- L3 ↔ spec-kit 的 spec 实体、OpenSpec 的 `design.md`
- **L5 骨架是现有框架普遍缺失的一级**——它们都是"文档 → 任务"，中间没有可运行验证
- L6 ↔ spec-kit 的 `tasks.md`（精确到文件 + 验证）
- L7 ↔ superpowers 的 `subagent-driven-development`（每任务新 subagent + 两阶段 review）

## 产出物

```
docs/frame/<slug>.md           # L1 六件套
docs/arch/01-architecture.md   # L2
docs/arch/02-contracts.md      # L3（S 档可省，改用代码类型）
docs/arch/03-decisions.md      # L4
docs/arch/04-tasks.md          # L6
```

S 档可把 01–04 并成一个 `<slug>.arch.md`。但**不要省掉 L3 和 L5**——它们是"便宜的证伪"，砍掉不是变快，是把纠错点从半小时推到三周后。
