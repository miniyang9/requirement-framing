# 两档模式：S（单人/单 agent）与 M（多人/多 agent）

## 怎么判定 S / M

**别用"体量大小"判，用"有没有并行面"判。**

| 判据 | 倾向 |
|---|---|
| 只有一个写者（你，或一个 agent） | **S** |
| 有 ≥2 个能同时开工、且各自能独立验收的面 | **M** |
| 所有人都在改同一个可执行体 | **S**——多写者挤在一条流水线上，拆开只增加协调成本 |
| 有人只做审查/验收，不写代码 | 仍是 **S**——review 不是并行面 |

一句话：**并行面 ≥ 2 且能各自独立验收 → 值得上 M；否则 S。**

体量大 ≠ 需要 M。一个三天的单线程流水线（抓取 → 排序 → 渲染 → 发送）是典型 S；两个人各自仓库改前后端，哪怕只有两天，也可能是 M。

⚠️ **产品侧多人 ≠ 执行侧多人**，这两件事经常被合成一个"多人任务"：

- **产品侧**：几个用户、要不要角色权限 → 归横切面第 2 项
- **执行侧**：几个写者、怎么切 → 归本节

"多用户"不推出 M 档；"一个人做"也不推出单租户设计。

## 一、为什么会有两档

两档要解决的**阻塞源不同**：

- **M 档**：信息不对称 → 靠契约把信息提前共享
- **S 档**：上下文衰减 + 自我欺骗 → 靠落盘和复读制造"记忆"与"证伪"

所以产物形态不同，但内核相同：**把运行时才能获得的信息，提前变成开工前就能拿到的信息。** S 档的"运行时"，是下一次上下文重置的那一刻。

## 二、逐级对照

| 级 | M 档作用 | S 档作用 | S 档形态 |
|---|---|---|---|
| L1 范围 | 对齐目标 | 防范围蔓延 | 一页 SPEC + **不做清单** |
| L2 架构 | 划分归属 | 防结构漂移 | 一页图，一屏能画完 |
| L3 契约 | 数据形状一致 | 防字段/术语静默漂移 | **代码里的类型**，不是文档 |
| L4 决策 | 选择一致 | 防"为什么这么写"失忆 | 一行一条，含"否决了什么" |
| L5 骨架 | 环境共用 | 最早的可运行反馈 | 最薄的垂直切片 |
| L6 切片 | 协调与验收 | 防"不知道做到哪" | 带完成判据，粒度 = 一次上下文 |
| L7 节奏 | 集成时序 | 防"改完就散" | 每片五步仪式 |

## 三、S 档：一个人扮演三个角色

单人项目里，你同时是**作者、审者、维护者**。三个角色要三件东西，缺哪个角色就瞎哪个：

| 角色 | 缺了会怎样 | 对应产物 |
|---|---|---|
| 作者 | 不知道要做什么 | SPEC + 垂直切片 |
| **审者** | **"跑通了"冒充"对了"** | 可执行验收 + 新上下文复读 |
| 维护者 | 三个月后不敢动 | 决策日志 + 运维手册 |

中间那个角色最容易被省略，因为它没有"产出物"——但它是唯一能挡住自我欺骗的东西。

## 四、S 档的每片五步

1. **读地图** — SPEC + 架构 + 最近三条决策 + 上次收尾记录
2. **只做一片** — 严格不管别的
3. **跑验收** — 可执行的，不是"看一眼觉得对"
4. **新上下文复读** — 产物 + 验收结果交给干净会话，只问"满足规格吗？哪里不对？"
5. **落盘** — 更新决策日志/地图，写三行收尾记录，提交

**第 4 步是单人可以免费获得 review 的唯一途径**，成本接近零。

第 5 步的收尾记录格式：

```
做了：<这一片实际完成到什么程度>
没做：<明确知道但留下的坑>
下次：<下一片从哪一行开始>
返工：<有返工则必填：哪一类 + 一句话；无则写"无">
```

第四行是**硬字段**：分类只有七种——理解 / 假设 / 验收不可测 / 切分丢约束 / 上下文丢失 / 实现跑偏 / **越线（签字前开工）**。这一行不写"故事"，只写分类，成本几秒钟；但它决定了三个月后你是否还知道自己的偏差通常发生在哪一跳。

它恰好填在上下文重置的那个缝里，比任何文档都实用。

## 五、S 档的六个死法

| 死法 | 早期信号 | 对策 |
|---|---|---|
| 上下文漂移 | 反复重新解释同一件事 | 约束落盘；每片开工先重读 |
| 自我欺骗 | "逻辑上应该对" | 验收必须是命令或固定夹具 |
| 决策失忆 | "为什么这块这么奇怪" | 决策日志，含否决项 |
| 范围蔓延 | 每片都比计划多做了点 | 不做清单；加东西要显式改 SPEC |
| 伪装成进展的重构 | 两周没跑过一次端到端 | 架构薄到一页；每片必须有可运行产物 |
| 地图腐坏 | 文档和代码对不上 | 文档只写"为什么"，"是什么"让代码说 |

## 六、混合模式

一个人 + 几个 agent，很常见。判据：

- **只有执行被并行，决策仍由一个人做** → 走 **M 档的 L3/L6/L7**，但 L2 可以薄
- **agent 之间要互相读对方产物** → 必须走 M 档全量
- **agent 只做一次性、互不相关的活** → 不需要契约，但仍需每张卡自带验收

## 七、升级信号（什么时候从 S 升到 M）

出现以下任一条，说明该升档：

1. 两个人（或两个 agent）要同时改同一个可执行体
2. 出现了"必须在 A 之后"的依赖链（说明缺契约）
3. 同一个概念在两个地方有两种叫法
4. 你需要向别人解释"为什么这么写"，且解释超过五句话
5. 一次上下文装不下一片

## 八、降级信号（什么时候 M 可以减配）

1. 只有一个人写代码，其他人只是看 → 契约可以只在代码里，不必单独成文
2. 总工作量 < 3 天 → L6 任务卡退化为一张清单
3. 变更是一次性的、不会被复用 → L4 决策日志可以只有三行

**不要为了流程完备而加级**：每一级都有成本，只有当它对应的阻塞源真实存在时才值得。
