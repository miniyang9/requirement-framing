## B 的入口（已定，2026-10-20）

B 的输入是**已签的 frame**，没有额外交接产物。

| 要素 | 规定 |
|---|---|
| **门禁** | 找不到 `状态：已签` 的 frame → **退回 L1**，不许就地脑补需求 |
| **先读哪节** | frame 的 `## 0. 承重事实`（十行以内），再读全文 |
| **状态判定** | 靠读 frame 顶部的 `状态：` 字段，不靠元数据 |
| **定位** | `docs/frame/` 攒多份之后怎么知道读哪份——**待定**（用户指认 / `index.md` / 最近已签） |

**为什么不需要交接块**：跨 session 时，"下游重读一遍已签的 frame"本身就是完整交接。真正要传的是**状态可判定**与**输入可定位**，不是内容副本。

**触发**（三段，逐一兜底）：
1. 同 session：A 的第 5 步直接点名"下一步调用 `solution-design`"
2. 跨 session：`~/.dsh/AGENTS.md` 加一条文件状态规则（"有已签 frame 且要求设计 → 先加载 B"）
3. 兜底：用户显式点名

## 建 B 之前要先回答的三个问题

1. **交接块够不够当 B 的输入？** 跑几次真实需求后看：哪些项 A 每次都空着（该删）、B 反复要而 A 没给（该加）。
2. **greenfield 和 brownfield 要不要分模式？** 两者方法差异大于"设计 vs 执行"，但触发时机相同——按 A 的经验，这类差异该做成模式开关，不该拆成两个 skill。
3. **哪些是判据、哪些只是模板？** 现有素材里"五个架构问题""契约判据""骨架三态"是判据；"任务卡 schema"是格式。B 的价值在判据，模板已经泛滥（BMAD / spec-kit / OpenSpec 都有）。
