## 1. 体量判定

**判定：多 epic 项目（粗估 20–40 个会话）。不是脚本，也不是平台。**

依据是它至少含五个能各自独立失败、且无法在一次会话里收敛的子系统：

| # | 子系统 | 它自己会怎么失败 |
|---|---|---|
| 1 | 设备与输入通道 | 坐标偏移、点击丢失、多实例抢焦点 |
| 2 | 屏幕采集与感知 | 分辨率/语言/皮肤变化导致识别静默失效 |
| 3 | 游戏状态机 | 遇到没见过的界面后行为未定义 |
| 4 | 决策 / 策略层 | 排程不合理，资源长期溢出或被浪费 |
| 5 | 运维与观测 | 挂了一夜，没人知道它在干活还是在乱点 |

**判定错一档的后果：**

- **判小（当成脚本）** → 第 4 个弹窗前面卡死，而且没有日志能解释它为什么停在那里。
- **判大（当成平台）** → 前两周在搭抽象层和设备接口，一次游戏都没点过。

## 4. 决策点

按"晚定的代价"降序。**D1 不定，后面全是空转。**

### D1 · 自动化程度（最重要）

| 档 | 内容 | 量级 | 主要风险 |
|---|---|---|---|
| A 收菜 | 收资源、补兵、点升级 | 3–5 会话 | 收益感弱，容易失去动力 |
| B 挂机刷资源 | 自动找对手、下兵、回城、循环 | 10–20 会话 | 战斗环节识别脆弱 |
| C 全自动上分 / 打部落战 | 需要战术决策与局面评估 | 30+ 会话 | 本质是博弈 + 视觉研究题 |

- **推荐**：产品上先做 B 的单模式最小闭环；但**架构按 C 预留**（状态机 + 世界快照）。这样不会因为选小了而返工。
- **可逆性**：架构可逆；产品定位（用哪个号、承担多少风险）不可逆。
- **晚定代价**：高。若 A 就够，B/C 的架构是纯过度设计。

### D2 · 账号风险策略

| 档 | 做法 | 风险 |
|---|---|---|
| A 小号实验 | 用不心疼的号，接受封号 | 低（情感与金钱成本） |
| B 主号人类化 | 随机化、作息、疲劳 | 降低但不消除 |
| C 只读不写 | 只识别与建议，点击由人做 | 零风险，收益小 |

- **推荐**：A 起步，验证链路；真要长期跑再考虑 B。
- **重要事实**：封号通常是**滞后批量**发生的，"跑了三个月没事"不构成安全性证据。
- **晚定代价**：高。决定输入层是否要做人类化（约 1.5 倍工作量）。

### D3 · 感知技术路线

| 档 | 手段 | 优点 | 代价 |
|---|---|---|---|
| A | 模板匹配 + OCR（OpenCV 一类） | 快、离线、便宜 | 对 UI 变化极脆，失效是静默的 |
| B | 多模态模型读屏 | 对变化鲁棒，能处理未知界面 | 慢（秒级）、要联网、有成本 |
| C | 混合：模板做状态识别，VLM 兜底未知状态与战斗决策 | 兼顾 | 两套都要维护 |

- **推荐**：C 的架构，A 的实现先行。即：先只用 A 打通闭环，但把"识别器"抽象成一个接口，B 随时可插入。
- **晚定代价**：中。选错会导致感知层重写。

### D4 · 输入通道

选项：ADB `input tap` / minitouch·maatouch（socket 注入）/ scrcpy 控制通道 / Windows 层鼠标模拟。

- **推荐**：scrcpy 或 minitouch。Windows 鼠标模拟在多实例和焦点切换下会出事。
- **晚定代价**：低（可替换），但影响"人类化"能做到多细（按压时长、滑动轨迹）。

### D5 · 部署形态

本地 Windows / 独立小主机 / 云手机。取决于**无人值守时长**与**是否多实例**。

- **推荐**：先本地，但把"设备接口"抽出来，后续能换。
- **晚定代价**：低。

### D6 · 是否先做"决策层"

升级排程、兵种配置、资源平衡，本质是**离线优化问题**，完全不碰游戏、零封号风险、可独立验证、且直接决定长期收益。

- **推荐**：**先做这个**。它是唯一一个"做完就一定有用、且不会被游戏更新搞坏"的模块。
- **晚定代价**：低（随时可加），但先做能让你在搭感知层之前就确认"这游戏值得自动化"。

## 5. 三种规模方案

| | A 最小可用 | B 正规工程（推荐） | C 平台化 |
|---|---|---|---|
| 周期 | ~1 周 | 4–8 周 | 3 个月+ |
| 范围 | 单模式、单账号、单分辨率 | 三层架构 + 未知兜底 + 复盘 + 看板 + 单账号长时间挂机 | 多账号 / 多游戏 / 远程管理 / 资产热更新 / VLM 兜底 |
| 放弃 | 鲁棒性、无人值守、多模式 | 多账号并发、战术级 AI | 短期可用性 |
| 锁死 | 若不做"世界快照"，B 阶段要重写 | 模板资产格式定下后，改造成本中等 | 大部分时间花在与目标无关的基础设施 |
| 何时选 | 只想确认"这条路通不通" | 你确实要长期用 | 你要给别人用 |

**我的推荐是 B，且 B 的第一步不是写业务代码，是做一个可行性探针**：固定模拟器与分辨率 → 抓 20 张关键界面截图 → 验证"模板能否稳定区分这些界面" → 验证"点击→状态变化"的延迟是否可观测。这个探针 1–2 天，但它决定后面 4 周是否白做。

## 6. 失败预演：最可能的三个死法

**死法 1 · 静默失效**
游戏更新或活动弹窗改了 UI，模板匹配度从 0.95 掉到 0.6，但仍高于你设的 0.5 阈值。它开始乱点，但日志里一切"正常"。
*最早信号*：未知状态率缓慢上升，没人看。
*对策*：置信度落入灰区即视为未知；未知即执行兜底动作并告警。

**死法 2 · 状态空间爆炸**
不断遇到新弹窗、新活动、新模式，每个都加一条特判。三个月后状态机 800 行，没人敢改。
*最早信号*：代码里全是 `if screen_hash == ...`。
*对策*：把"未知"当成一等公民。用一个"回到已知状态"的动作覆盖无穷多个未知界面，而不是枚举它们。

**死法 3 · 半途失去动力**
80% 的时间在查"它为什么点了空白处"，而你真正感兴趣的策略优化还没开始。
*最早信号*：第二周还在反复调坐标映射。
*对策*：把可视化 overlay（截图 + 识别框 + 当时的决策）放到最早做。它不是锦上添花，它是这个项目的开发速度本身。

| Q5 归属 | 自己用，但要有详细使用教程 | 确认，且教程升级为独立交付物（见 11.3） |
| 规模 | B 正规工程 | 确认 |
| 不做项 | 无推翻 | 确认 |

**这三处收缩是真实的**：不做人类化、暂不做无人值守、只做两个模式。

### 11.2 两个新事实，改写了风险排序

#### （1）Google Play Games（PC）≠ 安卓模拟器 ← 本轮最重要

我在 §0 把"模拟器"当成了前提，你的实际环境否掉了它。

- 它跑在 Google 的虚拟机里，**不是一个你能 `adb connect` 的安卓实例**。所以我原先给 D4 推荐的 **minitouch / scrcpy / `adb shell input` 很可能全部不可用**——三样都建立在 ADB 上。
- 剩下的只有 Windows 层：窗口捕获（DXGI Desktop Duplication / PrintWindow / BitBlt）+ 输入注入（SendInput）。
- **后果**：D4 从"晚定代价：低"直接变成**最高技术风险**，必须最先验证。
- 未知项：Windows 层注入能否被应用接受、能否做按压时长与滑动轨迹、是否被过滤。
- **一个乐观的线索**：Google Play Games PC 本身就为部分游戏提供键鼠映射。如果 CoC 在这个环境下能被鼠标正常操作，说明鼠标事件确实能被游戏消费，`SendInput` 大概率可行，P1 能过。
- **一个要澄清的点**：换成 Play Games PC **不改变** ToS 结论（自动化行为本身仍违反 Supercell 条款），它只改变了技术路径的可行性。

#### （2）"详细使用教程"不是文档工作，是可交接性

- 你自己用，所以这份教程的真实读者是**三个月后的你**：忘了怎么装、怎么改参数、卡住了怎么救。
- 因此它的形态不是"用户手册"，是**运维手册**：环境准备 / 参数含义 / 故障处置表 / 日志在哪看。
- 它和死法 3（半途失去动力）是同一件事的两面：**写不出运维文档，说明系统状态还依赖你的记忆**。
- **这是我原 16 项里漏掉的第 17 项。**

## 12. 一页项目定义

### 12.1 目标

在 Windows + Google Play Games(PC) 上，自动完成 Clash of Clans **主城与夜世界**的资源收取、部队训练、建筑升级与常规进攻循环；**人在旁边可随时接管**；并能通过运维手册与日志独立排障。

### 12.2 边界

- **做**：主城循环、夜世界循环、世界快照、未知状态兜底、动作日志与截图、运维手册、收益看板（可后置）
- **不做**：人类化伪装、无人值守、多账号、部落战战术、内存/改包、私服、分发

### 12.3 阶段（按风险降序）

| 阶段 | 内容 | 完成判据 | 会话 |
|---|---|---|---|
| **P1 设备层探针** | 验证 Windows 侧能截到画面、能注入点击 | 见 12.4 的判据 | 1–2 |
| P2 感知 + 状态机骨架 | 世界快照、5–8 个主状态识别、未知兜底、overlay | 20 张截图能正确分类；未知状态能兜底回主城 | 3–5 |
| P3 主城最小闭环 | 收菜 → 训练 → 找对手 → 下兵 → 回城 | 无人干预跑 30 分钟不卡死 | 4–6 |
| P4 夜世界闭环 | 第二套 UI 资产 | 同 P3 | 3–4 |
| P5 决策层（**可并行提前**） | 升级排程、兵种配置 | 给定资源状态输出建议，你认可 80% | 3–4 |
| P6 运维手册 + 看板 | 参数说明、故障处置表、日志 | 三个月后的你能照文档从零跑起来 | 2–3 |

**两点顺序说明：**

1. **主城先于夜世界**。收菜、训练、升级、常规进攻全在主城，夜世界是第二套 UI 资产 + 更慢的收益曲线。先主城能以更低成本验证整条链路。
2. **P5 不依赖任何阶段**，零封号风险、不会被游戏更新搞坏。想早点看到"有用"的东西，它可以和 P1 并行，甚至先于 P2。

### 12.4 第一个可验证切片 = P1，带终止条件

要回答的都是二值问题：

| # | 问题 | 通过标准 |
|---|---|---|
| 1 | 能否稳定截到游戏窗口？ | ≥5 fps，连续 60s 无黑屏 |
| 2 | 窗口分辨率能否固定？ | 重开游戏后客户区尺寸不变 |
| 3 | 能否注入点击并让游戏响应？ | 连续 20 次点击，20 次都有可见响应 |
| 4 | 输入→视觉变化延迟可测吗？ | 可测，且 < 500ms |
| 5 | 有没有 ADB / 调试通道？ | 有则方案大幅简化 |

**判据：**

- 1–4 全过 → 进 P2
- 3 或 4 不过 → **切平台**（BlueStacks / LDPlayer，ADB 可用）。架构不变，只换第 1 层
- 两个平台都做不到稳定注入 → 项目降级为 D2-C（只读不点，做辅助决策）
- 第 5 条为"有" → 直接走 ADB 路线，P1 半天结束

**P1 只产出一样东西**：一页记录（能不能截、能不能点、延迟多少、走哪条路）。不写业务代码，不搭架构。

### 12.5 整体验收

- 连续 2 小时主城循环不卡死，未知状态率 < 5%
- 每次动作都有截图，任意一次异常都能复盘
- 关掉进程重开能恢复，不需人工修状态
- 照运维手册，清空环境后能从零跑起来

### 12.6 三个要盯的指标

| 指标 | 为什么盯它 |
|---|---|
| 未知状态率 | 超过 5% 说明游戏在变，识别资产要更新 |
| 循环成功率 | 掉下来通常是设备层或时序问题，不是业务逻辑问题 |
| 每小时有效动作数 | 唯一能证明"它真的在干活"的指标 |

# 从需求到可派发任务（2026-10-20 追加）

## 14. 还差什么

**当前状态：只完成 L1。** 距"能切任务卡派发给子 agent"还有 6 级。

| 级 | 产出 | 门禁（过不了不许进下一级） | 状态 |
|---|---|---|---|
| L1 立项展开 | 本文档 §1–§12 | 体量、范围、风险排序已确认 | ✅ |
| L2 架构设计 | 分层、控制流、数据所有权、失败隔离 | 每一层都能独立测试 | ⬜ |
| L3 契约冻结 | 6 个 schema（见 14.2） | 每个 schema 有版本号与**唯一写者** | ⬜ |
| L4 方案设计 | 每模块的技术选择 + **被否决的替代方案** | 每个决定有理由，且记录了否决项 | ⬜ |
| L5 可运行骨架 | 端到端空壳，接口全通 | 一条命令跑起来，输出"我什么都没做" | ⬜ |
| L6 任务切片 | 任务卡 + 依赖 DAG | 每张卡可独立验收、不修改契约 | ⬜ |
| L7 派发与集成 | 并行组、合并节奏、两阶段 review | 一次只合一个任务，合完跑契约检查 | ⬜ |

### 14.1 为什么架构是并行的前提，而不是"进一步细化"

三个硬理由：

1. **并行的工作者之间没有共享上下文，唯一的共享物是契约。** 没有契约，三个子 agent 就是三份私有实现。
2. **命名权**。两个 agent 会各自发明状态名、字段名、目录结构。合并成本高于串行。
3. **决策一致性**。栈、坐标系、错误处理风格一旦各自选，集成期就是重写期。

这也是 superpowers 的 `subagent-driven-development` 能成立的原因：它前面有一道 `writing-plans`，产出"每个任务精确到文件路径 + 验证步骤"的计划。**没有那道计划，并行派发是灾难而非加速。**

### 14.2 六个必须冻结的契约（争用点，只能有一个写者）

| 契约 | 定义者 | 消费者 | 关键内容 |
|---|---|---|---|
| 世界快照 | 架构 | 感知 → 状态机 → 决策 | 状态 ID、资源、可用动作、置信度 |
| 状态词表 | 架构 | 感知、状态机 | 状态 ID 的**封闭集合** + 互斥规则 |
| 动作原语 | 架构 | 状态机 → 执行 | tap / swipe / wait_until / back，含超时语义 |
| 识别资产格式 | 感知 | 识别器、热更新 | 模板、区域、阈值、版本 |
| 事件日志 | 架构 | 全部 | JSONL 事件 schema |
| 配置 schema | 架构 | 决策、运维 | 参数、默认值、单位 |

### 14.3 五个必须在 L2 回答的架构问题

这五个不定，任务切不细——因为每一个都改变切分方式。

| # | 问题 | 影响 | 我的建议 |
|---|---|---|---|
| 1 | 坐标系：像素还是归一化比例？ | 决定识别资产能否跨分辨率复用 | **归一化**（按客户区比例）。像素坐标一改分辨率全废 |
| 2 | 时间语义：`sleep` 还是 `wait_until(条件, 超时)`？ | 决定执行器的接口形态 | **只允许 wait_until**，sleep 是最大不稳定源 |
| 3 | 状态判定：单帧还是 N 帧一致？ | 决定感知层要不要缓冲、状态机是否抖动 | **N 帧一致才转移**，否则动画中间帧会引发误判 |
| 4 | 置信度：二元还是分级？ | 决定"未知状态"是设计出来的还是碰运气 | **三级**：确定 / 灰区 / 未知。灰区触发再观察或兜底 |
| 5 | 决策：纯函数还是带内部状态？ | 决定它能否离线单测、能否并行开发 | **纯函数** `snapshot → action`，历史由外部注入 |

### 14.4 派发铁律

> 任务卡里若发现契约不足：**停下来报告，不许自行扩展契约。**

并行子 agent 的头号失败模式不是"做错"，而是"热心地各自改接口"。这一条比任何技术约束都重要。
