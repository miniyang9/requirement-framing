# 立项展开：每日 GitHub 热门 Top10 简报

> **档位：T1（轻量）** · 案例 3/3 · `requirement-framing` 的 L1 产物
> 本文件的作用之一是**证明门禁不压小活**：它只用了全量流程不到一半的篇幅，且跳过了 5 个层级。

## 0. 种子

> "写个自动化脚本，能在每天早上 8 点定时将 github 最热门的 top10 仓库简报发给我" `[你说过]`

## 1. 档位判定

| 判据 | 结果 |
|---|---|
| 可独立验证 | ✅ 一封消息就能验 |
| 单人 / 单产物 | ✅ |
| 预计工作量 | < 1 天 |
| 失败后果 | 可承受（今天没收到，明天还会有） |
| 是否需要并行 | ❌ |

→ **T1**。因此**不走** L2 架构、L3 契约、L4 决策日志、L6 任务卡、L7 派发。

**但保留两条不可省**：
1. **验收必须可执行**（T1 最容易死在这里）
2. **最大歧义必须在动手前解掉**（见 §2）

## 2. 最大歧义：「最热门」的口径

这是整个需求里唯一真正会做错的地方。三种实现，三个不同的产品：

| 口径 | 怎么实现 | 代价 |
|---|---|---|
| **今日 star 增量 Top10** | 自己每天记一次 star 数，算差分 | 最准；但**第一天没有数据**，要等两天才能出第一份简报 |
| **新仓库里最热**（`created:>7d` + `sort=stars`） | Search API 一次调用 | 最简单；但会漏掉“老仓库突然爆火” |
| **GitHub Trending 页面** | 抓 HTML 解析 | 最接近直觉；但**没有官方 API**，页面结构一变就坏 |

**不定这个，做出来的东西大概率不是你想要的那个。**

## 3. 一页五问

| 问 | 答 |
|---|---|
| **体量** | 半天到一天。一个定时任务 + 一个生成器 + 一个投递器 |
| **验收** | 连续 3 天在 8:05 前收到；每条含 仓库名 + 链接 + 一句话说明；**抓取失败要显式告警，不能静默**；同一天不重复发送 |
| **不做** | 历史归档、跨天去重、个性化推荐、Web UI、多语言摘要 |
| **最大歧义** | §2 的三个口径，选一个 |
| **失败怎么办** | 发一条“今天抓取失败”而不是什么都不发——静默失败会让你以为它还在工作 |

## 4. 隐含工作包

| # | 工作包 | 备注 |
|---|---|---|
| 1 | 取数 | 按 §2 选定口径。**需要 token**：未认证 60 次/小时，认证后 5000 次/小时 |
| 2 | 筛选 | 语言？只要新建仓库？排除 awesome-list 类？ |
| 3 | 生成简报 | 标题 + 链接 + 一句话。一句话是模板拼的还是模型写的？这决定要不要联网调模型、以及要不要处理失败 |
| 4 | 投递 | 邮件 / IM / 写文件？没有投递通道就等于没做完 |
| 5 | 定时 | 8:00 的时区；**机器那时是否开机**——本地定时任务的前提是机器不睡眠 |
| 6 | 幂等 | 重跑不能发两封 |
| 7 | 失败重试 | 取数失败重试几次？超时多久算失败？ |
| 8 | 日志 | 至少记：跑没跑、拿到几条、发没发出去 |

## 5. L5 判定：不需要独立骨架

本案例第一个可验证点是“手动跑一次，发给自己”。它**端到端**（贯穿取数→生成→投递）、**后果可承受**（发错了删掉即可）、**成本几分钟**。

所以它同时就是骨架、第一片和验收——**L5 与 L6 合并，不单独成级**。

> 这也给出了 L5 的判据边界：L5 存在的条件是“第一个端到端验证点很贵或不可逆”。不贵就合并，别为了流程完备凭空加一级。

## 6. 待你回答（3 个，够了）

**Q1（§2）** 「最热门」按哪个口径？
*推荐：**新仓库里最热**（`created:>7d` + `sort=stars`）。它一次调用就够、当天能出结果；等你想要“今日增量”时再加存储，那时你已经有历史数据了。*

**Q2（§4-4）** 发到哪？邮件 / 某个 IM / 写成本地文件？

**Q3（§4-5）** 8:00 时那台机器是开着的吗？
*如果答案是不确定 → 这一项就从“不适用”变成“必须做”，而且它会改变整个方案：本地 cron 换成云端定时任务。*

## 8. 复核与探测（2026-10-20 16:10 本机实测）

§2 的三种口径此前只是纸面比较。这一轮我把它们**跑了一遍**，因为"能不能取到数"决定了 Q1 是偏好题还是可行性题。

### 8.1 探测结果

| 探测项 | 结果 | 含义 |
|---|---|---|
| `api.github.com` from **python** / **node** | ✅ 200，core 60/h、search 10/min（未认证） | 取数可行；一天跑一次，额度绰绰有余 |
| `github.com/trending?since=daily` | ✅ 200，解析出 13 个仓库，含 `N stars today` | 口径 A 现在就能用 |
| `api.github.com` from **PowerShell / curl.exe** | ❌ `schannel: SEC_E_NO_CREDENTIALS` | **本机只用 Python 做网络请求**，不要用 PS 内建 HTTP 客户端 |
| `GITHUB_TOKEN` / `gh` CLI | 未设置 / 未安装 | 无 token 也能跑，但撞到限额只能等 |
| 本机时区 | America/Los_Angeles (PT) | "8:00" 若是北京时间 = **17:00 PT**，这个不问清会天天早/晚 9 小时 |

### 8.2 两个口径的真实样本（同一时刻）

| 口径 | Top 3 样本 |
|---|---|
| Trending 页面 | `MadsLorentzen/ai-job-search` +3,890 today · `cloudflare/security-audit-skill` +1,680 · `stablyai/orca` +1,559 |
| Search `created:>7d` | `deepseek-ai/DeepInfer` 11,950★ · `Gathin23/cleanyourtv` 11,500★ · `ly05010419/MacNativeGames` 2,768★ |

**两份名单几乎不重叠。** 所以这不是"实现细节"，是"你要哪种简报"——这正是 §2 说它是唯一真正会做错的地方的原因。

### 8.3 结论

三个口径**技术上全都能做**，差异在产品口味和长期维护成本：

- Trending 页面：最贴直觉，零 token，**但无官方 API**（页面改版就坏）→ 必须配"解析失败显式告警 + 兜底口径"。
- Search API：官方、稳定，但只覆盖新建仓库。
- 自记差分：最准，第一天出不了简报。

§6 的三个问题已被下面的 §9 取代（原文保留作历史）。

按"影响 × 不确定度"排序。每题我都给了推荐，直接说"按推荐"也能开工。
