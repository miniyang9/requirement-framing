# requirement-framing

把几句话的需求展开成可审查的规格，**在任何人开始拆任务之前**设一道门。同时兼容单人（单 agent）与多人（多 agent）场景。

一个纯内容的 skill：只有指令和参考文档，没有可执行代码，没有安装依赖。

## 适用范围（第 0 步就会判断）

**只用于软件工程**：交付物是代码，且能构建、运行、被运行结果验证。

| 需求 | 是否启用 |
|---|---|
| 脚本 / 服务 / 工具 / agent / 改造存量代码库 | ✅ 启用 |
| 方案 / 调研 / 汇报 / 文章 | ❌ 退化，不启用 |
| 活动策划、流程设计、组织安排 | ❌ 退化，不启用 |
| 混合（"产品含技术方案 + 运营方案"） | ⚠️ 只对软件部分启用，其余回正常沟通 |

**退化 ≠ 敷衍**：不建档、不判档位、不设门禁，但仍按正常对话澄清目标、给建议，并明确说一句"这不是软件工程类需求，我不启用立项展开"——让用户知道你**选择**了不启用，而不是漏了它。

## 它解决什么

用户用几句话描述一个工程，agent 常常直接分解成几个小任务——于是框架、方案、非功能、运维这些层面从未被讨论。这个 skill 强制先**展开**（横切面判定 + 隐含工作包 + 决策点 + 三档规模 + 失败预演），再**分档**决定要不要走后续的架构、契约、骨架、切片。

三条门禁：

1. 领域闸门未通过 → 全程不介入
2. 没有通过的 frame 文档 → 不许 plan、不许切任务、不许写代码
3. 展开阶段出现任务列表 → 本轮作废，重来

## 流程一览

```
第 0 步  领域闸门     交付物是能跑的代码吗？不是 → 退化
第 1 步  分流         T0 直接做 / T1 一页五问 / T2 全流程
第 2 步  L1 展开      六件套 + 17 项横切面 + ≤5 个问题（禁止任务列表）
第 3 步  人审签字     划掉 / 纠正 [推断] / 答问 / 选规模
第 4–7 步 L2–L7      按 S 档（单人）或 M 档（多人）展开
```

## 结构

```
requirement-framing/
├── skills/requirement-framing/
│   ├── SKILL.md              # 主干：信条 + 闸门 + 分流 + L0–L7 + 铁律
│   └── references/
│       ├── cross-sections.md # L1 的 17 项横切面判定表
│       ├── contracts.md      # L3 契约 / L5 骨架判据 / L6 任务卡 / L7 派发
│       └── modes.md          # S 档 vs M 档、升降级信号、单人六死法
├── CHANGELOG.md
├── LICENSE
└── README.md
```

`SKILL.md` 故意保持短，重内容按分支读 `references/`——避免一次塞满上下文。

## 怎么用

skill 的本质是"一个被发现的目录"，所以有三种用法，都没有安装步骤：

1. **拷进宿主的 skills 目录**：把 `skills/requirement-framing/` 整个复制过去，目录名与 `SKILL.md` 里的 `name` 一致即可
2. **当指令粘**：把 `SKILL.md` 的内容直接粘给任何 agent
3. **当仓库引用**：让 agent 读 `skills/requirement-framing/SKILL.md` 再按流程走

跨 harness 可移植：同一份 `SKILL.md`，凡支持 Agent Skills 的宿主都能读。

## 为什么不做成 plugin

plugin 的价值是**投递与生命周期**（npm 版本、一键启用/停用、marketplace、可执行钩子）；这个 skill 是纯内容，一项都用不上。做成 plugin 反而会把一份可移植的文档锁进宿主专属的 manifest 与 patch 里。

需要分发或版本管理时再包一层外壳即可，skill 本体不用改。
